产品化与差异化：做别人做不出来的那一半

目标：把前 17 周的能力包成一个有公开链接、首字 <2s、能看见过程、有成本看板的产品。

这一阶段是你相对其他候选人的结构性优势：大多数 AI 工程师做不出好前端，而 LLM 产品的成败很大程度在流式交互、延迟感知、错误可读性上。别人做不到，你能。

公开可访问的产品链接 生成式 UI 场景 限额 + 成本看板 3 个仓库的 README
先定一个原则：不做「聊天框 + 消息列表」

那是最容易做、也最没有区分度的形态。你要做的是把 agent 的过程变成界面的一部分：它在查什么、查到几条、为什么改了参数、花了多少钱。这件事只有懂前端的人做得好，也正好是面试官会记住的部分。

W18流式体验：延迟的感知比延迟本身重要

第 18 周 · 目标：首字 <2s，且用户在等待期间知道系统在做什么。

P5-1 技术选型：为什么是 Next.js + Vercel AI SDK 40min
为什么：你有前端底子，选型的核心不是「哪个最强」，是哪个能让你把时间花在交互而不是管道上。AI SDK 把流式协议、消息状态、工具调用渲染都处理了，你直接写 UI。
选择为什么代价
Next.js（App Router）你熟 React；流式 + Server Action 天然契合；部署路径最短RSC 的边界要理解清楚，否则会踩「在 client 里用 server 的东西」

后端（Python 的 RAG + loop）继续跑在自己机器或一个小 VPS 上，前端通过 HTTP 调它。不要在 Next.js 里重写一遍 Python 的检索逻辑——那是两周的浪费。

// app/api/chat/route.ts
import { streamText, convertToModelMessages, type UIMessage } from "ai";
import { openai } from "@ai-sdk/openai";

export const maxDuration = 60;

export async function POST(req: Request) {
  const { messages }: { messages: UIMessage[] } = await req.json();

  const result = streamText({
    model: openai("gpt-4.1-mini"),
    // v7：system 已改名 instructions（v6 及以前叫 system）
    instructions: "你是个人知识库助手。回答简洁，引用文件时写出文件名。",
    messages: convertToModelMessages(messages),
  });

  // v7：toUIMessageStreamResponse() 已标弃用。
  // 照官方 v7 文档换成等价写法，别照旧教程抄这一行。
  return result.toUIMessageStreamResponse();
}

// app/page.tsx
"use client";

import { useChat } from "@ai-sdk/react";
import { useState } from "react";

export default function Page() {
  const { messages, sendMessage, status, stop, error, regenerate } = useChat();
  const [input, setInput] = useState("");

  const busy = status === "streaming" || status === "submitted";

  return (
    <main className="mx-auto max-w-2xl p-6 space-y-6">
      <div className="space-y-4">
        {messages.map((m) => (
          <div key={m.id} className={m.role === "user" ? "text-right" : ""}>
            {m.parts.map((p, i) => {
              if (p.type === "text") {
                return (
                  <p key={i} className="whitespace-pre-wrap">{p.text}</p>
                );
              }
              return null; // 工具渲染见 P5-3
            })}
          </div>
        ))}
      </div>

      {error && (
        <div className="rounded border border-red-300 bg-red-50 p-3 text-sm">
          请求失败：{error.message}
          <button onClick={() => regenerate()} className="ml-2 underline">
            重试
          </button>
        </div>
      )}

      <form
        className="flex gap-2"
        onSubmit={(e) => {
          e.preventDefault();
          if (!input.trim() || busy) return;
          sendMessage({ text: input });
          setInput("");
        }}
      >
        <input
          className="flex-1 rounded border px-3 py-2"
          value={input}
          onChange={(e) => setInput(e.target.value)}
          placeholder="问点什么…"
        />
        {busy ? (
          <button type="button" onClick={stop} className="rounded bg-neutral-800 px-4 text-white">
            停止
          </button>
        ) : (
          <button type="submit" className="rounded bg-neutral-900 px-4 text-white">
            发送
          </button>
        )}
      </form>
    </main>
  );
}
三个必须知道的版本差异

① useChat 在 v5 之后不再管输入框状态——input/handleInputChange 要自己用 useState，发送改用 sendMessage({ text })。② 返回值从 toDataStreamResponse() 改名为 toUIMessageStreamResponse()。看到旧教程用错名字会报 500 或前端一直 loading。

③ v7（2026-07）又改了一批：system→instructions、onFinish→onEnd、fullStream→stream，toUIMessageStreamResponse() 进入弃用。你真正要做的是记住「这三代改名的方向」——名字永远会变，但「服务端产出流、客户端消费 parts」这个结构从 v4 到现在没变过。抓住结构，剩下的照着官方文档补。

产物两个文件 + 能逐字出字的界面
验收输入问题后文字逐字出现；点「停止」立刻中断；断网后能看到错误提示并能重试。
卡住怎么办
  • 一直 loading 不出字：先看 Network 里 /api/chat 的响应是流还是一整块 JSON。是一整块说明你用了 generateText 或忘了 streamText。
  • useChat is not exported：import 来源错。v4 是 ai/react，v5+ 是 @ai-sdk/react。
  • 消息重复渲染：parts 里已经包含文本和工具调用，别再额外渲染 content。

为什么：用户等待时最大的焦虑是「它到底在干嘛」。把工具调用过程可视化，感知延迟会显著下降——这不是装饰，是延迟优化手段。

// app/api/chat/route.ts（增量）
import { tool, stepCountIs } from "ai";
import { z } from "zod";

const tools = {
  search_knowledge: tool({
    description: "在个人知识库中检索。适合回答「文档里怎么写的」类问题。",
    inputSchema: z.object({
      query: z.string().describe("检索关键词"),
      top_k: z.number().int().min(1).max(10).default(5),
    }),
    execute: async ({ query, top_k }) => {
      // 调你的 Python 后端
      const r = await fetch(`${process.env.PY_API}/search`, {
        method: "POST",
        headers: { "content-type": "application/json" },
        body: JSON.stringify({ query, top_k }),
      });
      if (!r.ok) return { ok: false, error: `检索服务返回 ${r.status}` };
      const data = await r.json();
      // 关键：返回结构化结果，前端才能渲染成卡片而不是一段文字
      return { ok: true, chunks: data.chunks as { id: string; source: string; text: string }[] };
    },
  }),
};

  tools,
  stopWhen: stepCountIs(4),   // 最多 4 步，防前端无限请求

// components/ToolPart.tsx
"use client";

type AnyPart = {
  type: string;
  state?: string;
  input?: unknown;
  output?: unknown;
  errorText?: string;
};

export function ToolPart({ part }: { part: AnyPart }) {
  const name = part.type.replace(/^tool-/, "");

  if (part.state === "input-streaming" || part.state === "input-available") {
    return (
      <div className="flex items-center gap-2 text-sm text-neutral-500">
        <span className="inline-block h-2 w-2 animate-pulse rounded-full bg-blue-500" />
        正在调用 {name}…
      </div>
    );
  }

  if (part.state === "output-error" || part.errorText) {
    return (
      <div className="rounded border border-amber-300 bg-amber-50 p-2 text-sm">
        {name} 失败：{part.errorText ?? "未知错误"}
        <span className="ml-2 text-neutral-500">（可继续对话，我会换一种方式）</span>
      </div>
    );
  }

  const out = part.output as { ok?: boolean; chunks?: { source: string; text: string }[] };
  if (out?.chunks?.length) {
    return (
      <details className="rounded border p-2 text-sm">
        <summary className="cursor-pointer text-neutral-600">
          检索到 {out.chunks.length} 条
        </summary>
        <ul className="mt-2 space-y-1">
          {out.chunks.map((c, i) => (
            <li key={i} className="text-xs text-neutral-500">
              <b>{c.source}</b> · {c.text.slice(0, 90)}…
            </li>
          ))}
        </ul>
      </details>
    );
  }

  return null;
}

四步优化，按性价比排序
序优化预期收益代价
1立刻给出「正在检索」状态（哪怕只是三个点动画 + 一句话）感知延迟降 50%+，真实延迟不变几乎为零
2压缩输入：检索只取 top 3、单块 ≤600 字、去掉无关页眉TTFT 降 30–50%可能损失召回（用 eval 验证）
3并行：检索与「生成开场白」同时开始（先流一句「正在查你的笔记…」）感知再降一截代码复杂度上升
4把首轮换成小模型（路由），复杂问题第二步再升级TTFT 降 40%+需要质量验证
产物首字延迟的实测日志（至少 20 次）+ 优化前后对比
验收p50 首字 <1.5s，p95 <2.5s；能说出「主要耗时在输入 token 还是网络」。
卡住怎么办
  • 首字一直 >4s：先看 performance 里 TTFB（服务器响应开始时间）。如果 TTFB 就 3s，说明后端检索慢，不是前端问题。
  • 本地很快，部署后很慢：跨地域。前端在 Vercel、后端在本地 = 每次跨洋。把后端也部署到同一区域，或接受这个代价并诚实写进 README。
P5-5 中断、重试、错误可读：三态都要有出路 周日 1.5h
为什么：LLM 应用失败是常态（限流、超时、工具错）。把「失败」设计成一条死路还是设计成一个可继续的状态，这就是产品能力的差别。
状态用户看到什么能做什么实现
流式中逐字输出 + 停止按钮点停止，保留已生成内容stop()；注意服务端要能收到 abort
被中断「已停止」+ 重试 / 继续重试整轮，或「接着说完」regenerate()；「继续」需要把已有文本作为上下文
工具失败黄色提示 + 原因一句话自动重试一次，或让用户换个问法服务端不要抛异常，返回 { ok:false, error }
限流/超时「请求太频繁，10 秒后自动重试」+ 倒计时自动重试一次，失败则手动服务端退避（P4-3），前端显示倒计时
无权限「这部分资料你无权访问」说明范围，不要假装没找到后端返回明确错误码，前端区分文案
一个常见错误：把错误文案写成技术术语

「429 Too Many Requests」用户看不懂。改成「请求太频繁，请等 10 秒」。「fetch failed」改成「网络中断，已保留上面的内容，可以点重试」。错误文案是产品的一部分，不是日志的一部分。

产物五种状态的 UI + 一次人为制造 429 / 工具失败的录屏
验收五种状态都能触发并显示可操作的出路；没有任何一种会白屏或无限转圈。
卡住怎么办
  • 点停止后服务端还在跑（继续烧钱）：把 req.signal 传进 streamText 的 abortSignal，并让下游 fetch 也带这个 signal。
  • 重试后出现两条重复回答：regenerate() 是不带新消息的重生成；自己实现重试时要先移除最后一条 assistant 消息。

W19生成式 UI：让模型决定渲染什么

第 19 周 · 目标不是炫技，是让输出形态匹配内容——该是表格的别写成句子，该是卡片的别写成列表。

P5-6 方案 A：组件注册表（先做这个，稳且可控） 周六 3h
为什么先用注册表而不是 RSC 流式组件：注册表的思路是「模型返回 {component:"bar_chart", props:{...}}，前端查表渲染」。它有三个好处——可控（只有白名单组件）、可测（props 是数据，能校验）、可降级（组件不存在就显示文本）。RSC 方案更强但调试成本高，等你把这条跑通再说。
1. 定义允许的组件和它的 props schema
// lib/blocks.ts
import { z } from "zod";

export const blocks = {
  text: z.object({ body: z.string() }),

  source_list: z.object({
    items: z.array(z.object({
      title: z.string(),
      source: z.string(),
      snippet: z.string(),
    })).max(8),
  }),

  metric_row: z.object({
    items: z.array(z.object({
      label: z.string(),
      value: z.string(),
      delta: z.string().optional(),
    })).max(4),
  }),

  step_trace: z.object({
    steps: z.array(z.object({
      name: z.string(),
      status: z.enum(["ok", "fail", "skip"]),
      detail: z.string().optional(),
    })).max(10),
  }),

  code: z.object({ lang: z.string(), body: z.string() }),
};

export type BlockName = keyof typeof blocks;
export const BlockSchema = z.object({
  blocks: z.array(
    z.object({
      type: z.string(),
      props: z.record(z.string(), z.unknown()),
    })
  ).max(6),
});

          <span>{s.status === "ok" ? "✓" : s.status === "fail" ? "✕" : "–"}</span>
          <span className="font-medium">{s.name}</span>
          <span className="text-neutral-500">{s.detail}</span>
        </li>
      ))}
    </ol>
  ),

  code: (p) => (
    <pre className="overflow-x-auto rounded bg-neutral-900 p-3 text-xs text-neutral-100">
      <code>{String(p.body)}</code>
    </pre>
  ),
};

export function BlockRenderer({ blocks: list }: { blocks: { type: string; props: any }[] }) {
  return (
    <div className="space-y-3">
      {list.map((b, i) => {
        const render = Registry[b.type];
        // 关键：未知类型必须降级，不能白屏
        if (!render) return <p key={i}>{JSON.stringify(b.props)}</p>;
        const parsed = blocks[b.type as keyof typeof blocks]?.safeParse(b.props);
        if (!parsed?.success) return <p key={i}>{JSON.stringify(b.props)}</p>;
        return <div key={i}>{render(parsed.data)}</div>;
      })}
    </div>
  );
}

卡住怎么办
  • 模型总是只返回 text：system prompt 里给 2 个具体例子（「问资料 → source_list」），比列类型更有效。或者在 tool description 里写清触发条件。
  • blocks 数量爆炸（一次返回 6 个 text）：schema 里限制 .max(6) 并在 prompt 里说「能合并就合并」。
  • 想直接渲染 React 组件（RSC 方案）：那就是另一个复杂度级别。先把注册表做扎实——面试时这个方案的「可控性」论述反而更容易讲清。
P5-7 生成式 UI 的边界：什么时候不该用 周日 1h
为什么：能讲清「不该用的场景」的人，才是真懂。这份判断力在面试里比会用一个 API 值钱得多。
不该用的场景原因改用
需要精确对齐/可访问性的表单模型生成的字段顺序和校验规则不可控，无障碍语义难保证固定表单 + 模型只填默认值
高频重复的固定任务每次都让模型选组件是浪费延迟和钱写死模板，模型只填内容
数字/金额展示模型可能选错单位、四舍五入，风险高服务端算数，前端固定格式渲染
需要严格审计的界面「这次为什么显示这个组件」难以复现固定模板 + 记录渲染决策

判断口诀：内容形态不确定（可能是表格也可能是段落）→ 用生成式；内容形态确定但值不确定 → 用模板。

产物notes/generative-ui.md：你的使用边界 + 一个「我决定不用」的具体场景及理由
验收能回答「你这个功能如果用户量涨 100 倍，第一个崩的是哪里」——通常是每次问答都多一次结构化输出调用的成本。
卡住怎么办
  • 觉得「生成式 UI 就是高级感」：那说明还没找到真实需求。回到你的语料问一句：什么问题的答案用文字很别扭？从那里倒推该做什么组件。

P5-9 限额与多租户：超出预算要拒绝，而不是烧钱 周日 2h
为什么：一个公开链接 + 免费 API key = 有人会写脚本刷你。限额不是防坏人，是防你自己破产。同时它是「生产级」的标志之一。
// lib/ratelimit.ts —— 用 Postgres 做计数（不引入 Redis 也能跑）
import { sql } from "@/lib/db";

export async function checkQuota(userKey: string, costUsd: number) {
  const day = new Date().toISOString().slice(0, 10);
  const row = await sql`
    INSERT INTO usage_daily (user_key, day, calls, cost_usd)
    VALUES (${userKey}, ${day}, 1, ${costUsd})
    ON CONFLICT (user_key, day)
    DO UPDATE SET calls = usage_daily.calls + 1,
                  cost_usd = usage_daily.cost_usd + ${costUsd}
    RETURNING calls, cost_usd
  `;
  const { calls, cost_usd } = row[0];

  const LIMITS = { calls: 50, cost: 0.30 };   // 每用户每天
  if (calls > LIMITS.calls || Number(cost_usd) > LIMITS.cost) {
    return { ok: false, reason: "quota_exceeded" as const, calls, cost_usd };
  }
  return { ok: true as const, calls, cost_usd };
}
四层限额，从上到下越来越细
层限制什么实现
全局每分钟总请求数平台层（Vercel）或 Nginx limit_req
每用户每天调用次数 + 金额上面的 usage_daily
每次请求输入长度、max_tokens、最大步数route handler 里校验
每租户（数据）只能检索自己的文档检索 SQL 的 tenant_id（P2-11）
产物限额表 + checkQuota 接入 + 一次「超额被拒」的截图
验收连续调用超过 50 次后被拒绝，提示文案友好；数据库里能看到累计花费。
卡住怎么办
  • 没有用户系统，userKey 用什么：用 IP + 一个匿名 cookie UUID。够用了，别在这阶段做登录。
  • 成本拿不到（流式响应里 usage 在最后）：先按「每次请求固定估算」扣费，事后用实际 usage 校正。粗但可用。
P5-10 成本看板：一页看清钱花在哪 周日 1.5h
为什么：这是最容易被面试官记住的小细节——大多数个人项目只有一个聊天框，你有一个真实的运营视图。
指标SQL 口径看什么
今日花费SELECT sum(cost_usd) FROM usage_daily WHERE day=today是否接近预算
每次问答均成本sum(cost) / sum(calls)成本趋势（涨了说明上下文在膨胀）
P95 延迟percentile_cont(0.95) WITHIN GROUP (ORDER BY latency_ms)长尾
失败率count(status='error') / count(*)可靠性
拒答率count(refused) / count(*)太高=检索差，太低=可能瞎答

## 关键取舍

- **用手写 loop 而不是 LangGraph**：需要完整的步级控制（含审批中断）。

5闭卷自测

Q1–Q6 P5 阶段验收自测（点开看答题要点） 25min
Q1 为什么「流式」不只是体验问题，还是成本问题？

要点：流式让用户可在中途停止，避免为不需要的长回答付费；同时首字快意味着可以用更大的 max_tokens 而不担心等待；反过来，非流式必须等完整生成，超时就白花钱。

Q2 生成式 UI 的风险是什么？什么场景不该用？

要点：风险是不确定性（渲染错形态）、成本（多一次结构化输出调用）、可测性差（难断言）。不该用于：精确表单、固定高频任务、金额展示、强审计场景。

Q3 多租户 RAG 里，权限在哪一层做？为什么不能「检索完再过滤」？

要点：必须在检索 SQL 的 WHERE 里做。检索完再过滤的问题是：前 10 条可能全被过滤掉，用户看到「没找到」而实际有权限的文档排在第 30 位；另外无权限内容进了上下文就有泄露风险。

Q4 你的产品如果用户量涨 100 倍，第一个崩的是哪里？

要点：要给出具体判断，通常是「每次问答的模型调用成本」或「embedding 服务并发」。加分项：说出缓冲方案（缓存相同问题、批处理 embedding、把生成式 UI 的多余调用改成按需触发）。

Q5 你的 README 里为什么写「一条误答」？不会减分吗？

要点：不减分反而加分——它证明你做了评测且敢公开。招聘方最怕的是「不知道自己不知道」。关键是配套写清「已定位原因 + 下一步」。

Q6 首字延迟 4 秒，但用户反馈「还好」，你要不要优化？

要点：先确认「还好」是不是因为等待期间有可见反馈。如果是，说明感知管理有效，可以把优化优先级降低；但如果 p95 很差，长尾用户会流失。判断依据是数据不是感觉。

阶段通关条件

① 有公开可访问的链接且手机能打开；② 工具调用过程在界面上可见；③ 首字 p50 <1.5s；④ 超额请求被拒且提示友好；⑤ 成本看板能报出今日花费；⑥ README 六块齐全，陌生人 3 分钟能复述。
