开始之前：这一阶段要懂的 9 个概念

这一页不只有动手。下面每张卡都会用到这几个心智模型——概念先立住，命令才不是照抄；概念没立住，改一行代码就不知道会牵动哪里。

先定一个原则：不做「聊天框 + 消息列表」

W18流式体验：延迟的感知比延迟本身重要

第 18 周 · 目标：首字 <2s，且用户在等待期间知道系统在做什么。

P5-1 技术选型：为什么是 Next.js + Vercel AI SDK 40min
为什么：你有前端底子，选型的核心不是「哪个最强」，是哪个能让你把时间花在交互而不是管道上。AI SDK 把流式协议、消息状态、工具调用渲染都处理了，你直接写 UI。
选择为什么代价
Next.js（App Router）你熟 React；流式 + Server Action 天然契合；部署路径最短RSC 的边界要理解清楚，否则会踩「在 client 里用 server 的东西」
Vercel AI SDK 7
2026-07 发布		useChat 管消息状态、streamText 管流式、tool part 自动带类型；v7 起工具循环有现成的 ToolLoopAgent 类破坏性升级：Node 22 起、只支持 ESM。system→instructions、onFinish→onEnd、fullStream→stream，toUIMessageStreamResponse() 已标弃用。见下方 P5-2 的版本说明
Tailwind迭代 UI 快，不用维护 CSS 文件类名长；团队协作需要约定
Zodtool 的 inputSchema 用它，和 TS 类型自动对齐无

版本核对（2026-10）：你装到的是 v7，不是 v6

AI SDK 7 在 2026 年 7 月发布，把 agent 变成了一等公民（ToolLoopAgent / WorkflowAgent / HarnessAgent），代价是一次硬破坏：Node 22 最低、只支持 ESM，并且改了几个高频名字。

下面 P5-2 的代码按语义读，不要逐字照抄——先跑 npm ls ai 确认版本，再对照官方 v7 文档。网上绝大多数教程还停在 v5/v6。官方提供 npx @ai-sdk/codemod v7 做机械迁移，但它覆盖不到所有调用点。

后端（Python 的 RAG + loop）继续跑在自己机器或一个小 VPS 上，前端通过 HTTP 调它。不要在 Next.js 里重写一遍 Python 的检索逻辑——那是两周的浪费。

卡住怎么办
  • 装完发现 API 和教程对不上：先 npm ls ai 看实际版本，再按该版本文档写。AI SDK 的 breaking change 很频繁，这是常态。
  • 想用 Vue/Svelte：也行，但 AI SDK 的 React 生态最全（tool part 渲染、useChat 的成熟度）。这阶段别给自己加难度。
P5-2 流式最小闭环：两个文件跑通 周六 2h
为什么：先跑通「打字机效果」，再谈其他。很多人第一天就想做工具可视化，结果卡在流式协议上三天。
关键知识点

流式改的是感知，不是总时长。 生成 500 字，流式和非流式的总耗时都是 8 秒。差别在用户多久看到第一个字：非流式是 8 秒后一次性出现，流式是 0.5 秒开始逐字出现。前者让人怀疑卡死并刷新页面，后者让人愿意等——这就是为什么它值得做。

  • 两个指标要分开优化：TTFT（首字时间）决定留存，总时长决定成本与并发占用。把两者混成「加载时间」，就不知道该往哪改。
  • 为什么选 SSE 不选 WebSocket：单向推送用 SSE 就是一条不关闭的 HTTP 响应，能过大多数代理、断线浏览器自动重连、实现只要几十行。为「以后可能要双向」上 WebSocket，是典型的过度设计。
  • 必须处理的细节：流式下的错误发生在中途——HTTP 状态码早就是 200 了，错误只能放在流里传（最后一个 event 带 error 字段），前端要能识别并给出出路（P5-5）。
服务端：一个 route handler
// app/api/chat/route.ts
import { streamText, convertToModelMessages, type UIMessage } from "ai";
import { openai } from "@ai-sdk/openai";

export const maxDuration = 60;

export async function POST(req: Request) {
  const { messages }: { messages: UIMessage[] } = await req.json();

  const result = streamText({
    model: openai("gpt-4.1-mini"),
    // v7：system 已改名 instructions（v6 及以前叫 system）
    instructions: "你是个人知识库助手。回答简洁，引用文件时写出文件名。",
    messages: convertToModelMessages(messages),
  });

  // v7：toUIMessageStreamResponse() 已标弃用。
  // 照官方 v7 文档换成等价写法，别照旧教程抄这一行。
  return result.toUIMessageStreamResponse();
}
客户端：useChat + 渲染 parts
// app/page.tsx
"use client";

import { useChat } from "@ai-sdk/react";
import { useState } from "react";

export default function Page() {
  const { messages, sendMessage, status, stop, error, regenerate } = useChat();
  const [input, setInput] = useState("");

  const busy = status === "streaming" || status === "submitted";
  // 两个状态都算忙：submitted 是「已发出、还没收到第一个字」，
  // 这段时间不锁输入，用户会连点三次，花三份钱。

  return (
    <main className="mx-auto max-w-2xl p-6 space-y-6">
      <div className="space-y-4">
        {messages.map((m) => (
          <div key={m.id} className={m.role === "user" ? "text-right" : ""}>
            // 消息不是一个字符串，是 parts 数组：文本、工具调用各占一段。
            // 只读 m.content 会把工具那一段整个丢掉。
            {m.parts.map((p, i) => {
              if (p.type === "text") {
                return (
                  <p key={i} className="whitespace-pre-wrap">{p.text}</p>
                );
              }
              return null; // 工具渲染见 P5-3
            })}
          </div>
        ))}
      </div>

      // 错误必须渲染到界面上：流式中断只打 console 的话，用户只会以为「卡了」，然后刷新重来
      {error && (
        <div className="rounded border border-red-300 bg-red-50 p-3 text-sm">
          请求失败：{error.message}
          <button onClick={() => regenerate()} className="ml-2 underline">
            重试
          </button>
        </div>
      )}

      <form
        className="flex gap-2"
        onSubmit={(e) => {
          e.preventDefault();
          if (!input.trim() || busy) return;
          sendMessage({ text: input });
          setInput("");
        }}
      >
        <input
          className="flex-1 rounded border px-3 py-2"
          value={input}
          onChange={(e) => setInput(e.target.value)}
          placeholder="问点什么…"
        />
        // 流式期间必须给「停止」：不给的话用户只能刷新页面，而这次请求的 token 照样计费
        {busy ? (
          <button type="button" onClick={stop} className="rounded bg-neutral-800 px-4 text-white">
            停止
          </button>
        ) : (
          <button type="submit" className="rounded bg-neutral-900 px-4 text-white">
            发送
          </button>
        )}
      </form>
    </main>
  );
}
三个必须知道的版本差异

① useChat 在 v5 之后不再管输入框状态——input/handleInputChange 要自己用 useState，发送改用 sendMessage({ text })。② 返回值从 toDataStreamResponse() 改名为 toUIMessageStreamResponse()。看到旧教程用错名字会报 500 或前端一直 loading。

③ v7（2026-07）又改了一批：system→instructions、onFinish→onEnd、fullStream→stream，toUIMessageStreamResponse() 进入弃用。你真正要做的是记住「这三代改名的方向」——名字永远会变，但「服务端产出流、客户端消费 parts」这个结构从 v4 到现在没变过。抓住结构，剩下的照着官方文档补。

产物两个文件 + 能逐字出字的界面
验收输入问题后文字逐字出现；点「停止」立刻中断；断网后能看到错误提示并能重试。
卡住怎么办
  • 一直 loading 不出字：先看 Network 里 /api/chat 的响应是流还是一整块 JSON。是一整块说明你用了 generateText 或忘了 streamText。
  • useChat is not exported：import 来源错。v4 是 ai/react，v5+ 是 @ai-sdk/react。
  • 消息重复渲染：parts 里已经包含文本和工具调用，别再额外渲染 content。
P5-3 把「它在做什么」变成界面（本阶段最有区分度的一张卡） 周六 2.5h
为什么：用户等待时最大的焦虑是「它到底在干嘛」。把工具调用过程可视化，感知延迟会显著下降——这不是装饰，是延迟优化手段。
服务端：定义工具（带 execute）
// app/api/chat/route.ts（增量）
import { tool, stepCountIs } from "ai";
import { z } from "zod";

// description 和参数说明会原样发给模型，和 P1 的 tools.py 是同一份协议，
// 只是这里用 zod 写、由 SDK 生成 JSON Schema。
const tools = {
  search_knowledge: tool({
    description: "在个人知识库中检索。适合回答「文档里怎么写的」类问题。",
    inputSchema: z.object({
      query: z.string().describe("检索关键词"),
      top_k: z.number().int().min(1).max(10).default(5),
    }),
    // execute 里不要往外抛异常：返回 { ok: false } 让模型自己读错误、换策略，
    // 和后端 loop 的处理纪律保持一致。
    execute: async ({ query, top_k }) => {
      // 调你的 Python 后端
      const r = await fetch(`${process.env.PY_API}/search`, {
        method: "POST",
        headers: { "content-type": "application/json" },
        body: JSON.stringify({ query, top_k }),
      });
      if (!r.ok) return { ok: false, error: `检索服务返回 ${r.status}` };
      const data = await r.json();
      // 关键：返回结构化结果，前端才能渲染成卡片而不是一段文字
      return { ok: true, chunks: data.chunks as { id: string; source: string; text: string }[] };
    },
  }),
};

// stepCountIs 是这一层唯一的预算闸：前端没有 max_steps，多轮工具调用只能靠它挡住
const result = streamText({
  model: openai("gpt-4.1-mini"),
  system: SYSTEM,
  messages: convertToModelMessages(messages),
  tools,
  stopWhen: stepCountIs(4),   // 最多 4 步，防前端无限请求

客户端：按 part 类型渲染不同 UI
// components/ToolPart.tsx
"use client";

type AnyPart = {
  type: string;
  state?: string;
  input?: unknown;
  output?: unknown;
  errorText?: string;
};

export function ToolPart({ part }: { part: AnyPart }) {
  const name = part.type.replace(/^tool-/, "");
  // 工具段在 parts 里的 type 是 tool-<名字>，去掉前缀才对得上 Registry 里的工具名

  // 参数还没拼完就先显示「正在调用」：这几十毫秒决定了用户觉不觉得系统在动
  if (part.state === "input-streaming" || part.state === "input-available") {
    return (
      <div className="flex items-center gap-2 text-sm text-neutral-500">
        <span className="inline-block h-2 w-2 animate-pulse rounded-full bg-blue-500" />
        正在调用 {name}…
      </div>
    );
  }

  // 工具失败要显式渲染出来，并且告诉用户「可以继续」：不显示的话，他会以为刚才那步成功了
  if (part.state === "output-error" || part.errorText) {
    return (
      <div className="rounded border border-amber-300 bg-amber-50 p-2 text-sm">
        {name} 失败：{part.errorText ?? "未知错误"}
        <span className="ml-2 text-neutral-500">（可继续对话，我会换一种方式）</span>
      </div>
    );
  }

  // 只按契约里的字段读，不做防御式兜底：契约变了要让它在这里报错，
  // 而不是静默渲染成空——空的卡片比崩溃更难查。
  const out = part.output as { ok?: boolean; chunks?: { source: string; text: string }[] };
  if (out?.chunks?.length) {
    return (
      <details className="rounded border p-2 text-sm">
        <summary className="cursor-pointer text-neutral-600">
          检索到 {out.chunks.length} 条
        </summary>
        <ul className="mt-2 space-y-1">
          {out.chunks.map((c, i) => (
            <li key={i} className="text-xs text-neutral-500">
              <b>{c.source}</b> · {c.text.slice(0, 90)}…
            </li>
          ))}
        </ul>
      </details>
    );
  }

  return null;
}

四步优化，按性价比排序
序优化预期收益代价
1立刻给出「正在检索」状态（哪怕只是三个点动画 + 一句话）感知延迟降 50%+，真实延迟不变几乎为零
2压缩输入：检索只取 top 3、单块 ≤600 字、去掉无关页眉TTFT 降 30–50%可能损失召回（用 eval 验证）
3并行：检索与「生成开场白」同时开始（先流一句「正在查你的笔记…」）感知再降一截代码复杂度上升
4把首轮换成小模型（路由），复杂问题第二步再升级TTFT 降 40%+需要质量验证

卡住怎么办
  • 首字一直 >4s：先看 performance 里 TTFB（服务器响应开始时间）。如果 TTFB 就 3s，说明后端检索慢，不是前端问题。
  • 本地很快，部署后很慢：跨地域。前端在 Vercel、后端在本地 = 每次跨洋。把后端也部署到同一区域，或接受这个代价并诚实写进 README。
P5-5 中断、重试、错误可读：三态都要有出路 周日 1.5h
为什么：LLM 应用失败是常态（限流、超时、工具错）。把「失败」设计成一条死路还是设计成一个可继续的状态，这就是产品能力的差别。
状态用户看到什么能做什么实现
流式中逐字输出 + 停止按钮点停止，保留已生成内容stop()；注意服务端要能收到 abort
被中断「已停止」+ 重试 / 继续重试整轮，或「接着说完」regenerate()；「继续」需要把已有文本作为上下文
工具失败黄色提示 + 原因一句话自动重试一次，或让用户换个问法服务端不要抛异常，返回 { ok:false, error }
限流/超时「请求太频繁，10 秒后自动重试」+ 倒计时自动重试一次，失败则手动服务端退避（P4-3），前端显示倒计时
无权限「这部分资料你无权访问」说明范围，不要假装没找到后端返回明确错误码，前端区分文案
一个常见错误：把错误文案写成技术术语

「429 Too Many Requests」用户看不懂。改成「请求太频繁，请等 10 秒」。「fetch failed」改成「网络中断，已保留上面的内容，可以点重试」。错误文案是产品的一部分，不是日志的一部分。

产物五种状态的 UI + 一次人为制造 429 / 工具失败的录屏
验收五种状态都能触发并显示可操作的出路；没有任何一种会白屏或无限转圈。
卡住怎么办
  • 点停止后服务端还在跑（继续烧钱）：把 req.signal 传进 streamText 的 abortSignal，并让下游 fetch 也带这个 signal。
  • 重试后出现两条重复回答：regenerate() 是不带新消息的重生成；自己实现重试时要先移除最后一条 assistant 消息。

W19生成式 UI：让模型决定渲染什么

第 19 周 · 目标不是炫技，是让输出形态匹配内容——该是表格的别写成句子，该是卡片的别写成列表。

P5-6 方案 A：组件注册表（先做这个，稳且可控） 周六 3h
为什么先用注册表而不是 RSC 流式组件：注册表的思路是「模型返回 {component:"bar_chart", props:{...}}，前端查表渲染」。它有三个好处——可控（只有白名单组件）、可测（props 是数据，能校验）、可降级（组件不存在就显示文本）。RSC 方案更强但调试成本高，等你把这条跑通再说。
关键知识点

组件注册表是安全边界，不是设计偏好。 生成式 UI 的本质是让模型决定「渲染什么」。如果模型输出的是 HTML/JS 字符串，你等于把页面的执行权交给了它——而它的输入里可能藏着别人写的文档（提示注入，P4-4）。注册表把这个问题变成了白名单问题：模型只能输出 {"component": "BarChart"}，名字不在这张表里就丢弃。

  • 模型永远碰不到 DOM。它产出的是「组件名 + 参数」，由你的代码去渲染。这一条是方案 A「稳且可控」的全部含义。
  • props 也要约束：每个组件声明自己的 schema，模型给的参数先校验再渲染。校验失败就降级成纯文本答案，不要让页面白屏。
  • 能力边界由你写死，不由模型的想象力决定：少一个组件只是少一种呈现方式；多一个口子可能是整站 XSS。取舍方向很明确。
1. 定义允许的组件和它的 props schema
// lib/blocks.ts
import { z } from "zod";

// 每种块一个 schema。.max(n) 是给模型的硬上限：不设上限，
// 它一次能生成 40 条引用，前端直接卡死。
export const blocks = {
  text: z.object({ body: z.string() }),

  source_list: z.object({
    items: z.array(z.object({
      title: z.string(),
      source: z.string(),
      snippet: z.string(),
    })).max(8),
  }),

  metric_row: z.object({
    items: z.array(z.object({
      label: z.string(),
      value: z.string(),
      delta: z.string().optional(),
    })).max(4),
  }),

  step_trace: z.object({
    steps: z.array(z.object({
      name: z.string(),
      status: z.enum(["ok", "fail", "skip"]),
      detail: z.string().optional(),
    })).max(10),
  }),

  code: z.object({ lang: z.string(), body: z.string() }),
};

// 类型名从 schema 反推：加一种块只改上面一处，这里自动跟着变
export type BlockName = keyof typeof blocks;
// 外层 schema 故意写松（type 是 string、props 任意）：真正的校验在渲染时按 type 分派，
// 这样新增块类型不用改 prompt 里那份 schema。
export const BlockSchema = z.object({
  blocks: z.array(
    z.object({
      type: z.string(),
      props: z.record(z.string(), z.unknown()),
    })
  ).max(6),
});

3. 前端查表渲染，未知类型降级为文本
// components/BlockRenderer.tsx
"use client";

import { blocks } from "@/lib/blocks";

// 一个 type 对应一个渲染函数：加块类型只在这里加一行，主流程不用动
const Registry: Record<string, (p: any) => React.ReactNode> = {
  text: (p) => <p className="whitespace-pre-wrap">{String(p.body)}</p>,

  source_list: (p) => (
    <ul className="space-y-2">
      {(p.items ?? []).map((it: any, i: number) => (
        <li key={i} className="rounded border p-2 text-sm">
          <div className="font-medium">{it.title}</div>
          <div className="text-xs text-neutral-500">{it.source} · {it.snippet}</div>
        </li>
      ))}
    </ul>
  ),

  metric_row: (p) => (
    <div className="grid grid-cols-2 gap-2 sm:grid-cols-4">
      {(p.items ?? []).map((it: any, i: number) => (
        <div key={i} className="rounded border p-3">
          <div className="text-xs text-neutral-500">{it.label}</div>
          <div className="text-lg font-semibold">{it.value}</div>
          {it.delta && <div className="text-xs">{it.delta}</div>}
        </div>
      ))}
    </div>
  ),

  step_trace: (p) => (
    <ol className="space-y-1 text-sm">
      {(p.steps ?? []).map((s: any, i: number) => (
        <li key={i} className="flex gap-2">
          <span>{s.status === "ok" ? "✓" : s.status === "fail" ? "✕" : "–"}</span>
          <span className="font-medium">{s.name}</span>
          <span className="text-neutral-500">{s.detail}</span>
        </li>
      ))}
    </ol>
  ),

  code: (p) => (
    <pre className="overflow-x-auto rounded bg-neutral-900 p-3 text-xs text-neutral-100">
      <code>{String(p.body)}</code>
    </pre>
  ),
};

export function BlockRenderer({ blocks: list }: { blocks: { type: string; props: any }[] }) {
  return (
    <div className="space-y-3">
      {list.map((b, i) => {
        const render = Registry[b.type];
        // 关键：未知类型必须降级，不能白屏
        if (!render) return <p key={i}>{JSON.stringify(b.props)}</p>;
        // 渲染前按 type 再校一次：模型给的 props 不可信，schema 过了才交给组件
        const parsed = blocks[b.type as keyof typeof blocks]?.safeParse(b.props);
        if (!parsed?.success) return <p key={i}>{JSON.stringify(b.props)}</p>;
        return <div key={i}>{render(parsed.data)}</div>;
      })}
    </div>
  );
}

P5-7 生成式 UI 的边界：什么时候不该用 周日 1h
为什么：能讲清「不该用的场景」的人，才是真懂。这份判断力在面试里比会用一个 API 值钱得多。
不该用的场景原因改用
需要精确对齐/可访问性的表单模型生成的字段顺序和校验规则不可控，无障碍语义难保证固定表单 + 模型只填默认值

判断口诀：内容形态不确定（可能是表格也可能是段落）→ 用生成式；内容形态确定但值不确定 → 用模板。

卡住怎么办
  • 觉得「生成式 UI 就是高级感」：那说明还没找到真实需求。回到你的语料问一句：什么问题的答案用文字很别扭？从那里倒推该做什么组件。

// lib/ratelimit.ts —— 用 Postgres 做计数（不引入 Redis 也能跑）
import { sql } from "@/lib/db";

export async function checkQuota(userKey: string, costUsd: number) {
  // 用 UTC 日期切天：用本地时区的话，跨时区或夏令时会凭空多出、少掉一小时额度
  const day = new Date().toISOString().slice(0, 10);
  // 计数和判断压成一条 SQL：INSERT … ON CONFLICT DO UPDATE … RETURNING 拿到的是加完之后的值。
  // 「先查再写」在并发下会漏计。
  const row = await sql`
    INSERT INTO usage_daily (user_key, day, calls, cost_usd)
    VALUES (${userKey}, ${day}, 1, ${costUsd})
    ON CONFLICT (user_key, day)
    DO UPDATE SET calls = usage_daily.calls + 1,
                  cost_usd = usage_daily.cost_usd + ${costUsd}
    RETURNING calls, cost_usd
  `;
  const { calls, cost_usd } = row[0];

  // 双限额：只限次数会被「一次调用跑 20 轮」绕过；只限金额又挡不住刷接口
  const LIMITS = { calls: 50, cost: 0.30 };   // 每用户每天
  if (calls > LIMITS.calls || Number(cost_usd) > LIMITS.cost) {
    return { ok: false, reason: "quota_exceeded" as const, calls, cost_usd };
  }
  return { ok: true as const, calls, cost_usd };
}

P5-14 消融：证明每个特性真的有用（连带双层开关） 周日 2.5h
为什么：到 W20 你的系统已经上线，堆了七八个特性——查询改写、混合检索、重排、自检、缓存、路由。W17 只证明了「改完变便宜、变快」，没证明每个特性各自值多少。做真消融的三个前提这时才齐：真实流量、成本看板、一套跑得动的 eval。「加了之后感觉更好了」是最常见的自欺：可能真有效，也可能同时改了 prompt；可能这次样本运气好，也可能它在中位数上更好但尾部长了。消融是唯一能回答「这个特性到底值多少」的方法，也是面试里「你做的哪个优化最有效」这个问题的唯一诚实答法。

这一张先测最贵的四个（改写 / 重排 / 自检 / 缓存）——路由的质量代价在 P4-9 的分组对照表里已经单独验过，不重复测。AB 分流要真实用户，也正好从这一周开始才做得了。

消融：一次只关一个，其余不动
做法能回答不能回答
全开 vs 全关这套东西整体有没有用哪个特性有用、哪个白花钱
单特性消融（一次关一个）每个特性的边际贡献特性之间的耦合
AB 测试（真实用户分流）业务指标有没有变好小流量下很难达到显著

顺序是固定的：先消融定位，再 AB 验证。跳过消融直接 AB，你会在结论里看到「整体变好了 2%」，然后完全不知道是该保留还是砍掉其中一半。

双层开关：能关掉，才敢上线
"""src/agentlab/flags.py — 任何特性都必须能被单独关掉"""
from __future__ import annotations

import os
from dataclasses import dataclass, replace


@dataclass(frozen=True)
class Flags:
    query_rewrite: bool = True     # 查询改写
    rerank: bool = True            # 交叉编码器重排
    self_check: bool = False       # 答案自检（多一次调用，贵）
    cache_prefix: bool = True      # 稳定前缀缓存


def load(remote: dict[str, bool] | None = None) -> Flags:
    """优先级：远程配置 > 环境变量 > 代码默认。

    远程这一层是给「线上出问题、不想等发版」准备的。
    没有这一层，回滚就要走一次发布流程。
    """
    remote = remote or {}
    kwargs = {}
    for f in Flags.__dataclass_fields__:
        if f in remote:
            kwargs[f] = bool(remote[f])
        elif os.getenv(f"AIP_{f.upper()}"):
            kwargs[f] = os.getenv(f"AIP_{f.upper()}") == "1"
    return replace(Flags(), **kwargs)

for f in ("query_rewrite", "rerank", "self_check", "cache_prefix"):
    on = run_eval(flags=BASE)
    off = run_eval(flags=replace(BASE, **{f: False}))
    d_pass5 = on.pass5 - off.pass5
    d_cost = on.cost - off.cost
    print(f"{f:14s} Pass@5 {d_pass5:+.3f}  成本 {d_cost:+.4f}  延迟 {on.p95 - off.p95:+.0f}ms")

这套开关 W21 的「灰度与回滚」（P5-13）会直接复用：机制只建一次，那里只讲怎么用它放量和退回。

看三个数，不只看一个

一个特性「让 Pass@5 涨 2 个点、成本涨 60%、延迟涨 800ms」，那不叫有用，那叫贵。要求每个特性都同时给出 质量 / 成本 / 延迟 三个 delta，然后自己回答「这个交换值不值」。只报质量提升的消融是不完整的。

产物src/agentlab/flags.py + scripts/ablate.py + notes/ablation.md：4 个特性的三列 delta 表 + 一句「哪个该砍」的结论
验收 表里必须有一个特性是负作用或零作用——真实系统里几乎总有。找到它、砍掉它、再跑一次 eval 确认没变差。「我加的每个特性都有用」这句话本身就是没做消融的证据。另外验收两条工程硬要求：① 所有特性都能用环境变量单独关掉；② 关掉后不需要改代码、不需要重新部署。
卡住怎么办
  • 每个特性都是正作用：样本太少或噪声太大。先按 P2-16 把样本量提到 20 题 × 3 次。
  • 关掉某特性后 eval 反而变好：这是最好的发现，别怀疑数据。先确认不是评测器偏差（人工看 3 条轨迹），然后砍。
  • 特性互相依赖，关不掉：说明开关粒度不对。把「重排」和「混合检索」拆成两个独立开关——耦合的开关等于没开关。

P5-13 上线之后：四种更新载体与灰度回滚 周日 3h
为什么：W21 你有了一个能打开的作品，但作品和产品的差别是它能不能在没人管的情况下继续变好。上线后系统一定会退化：模型被升级、用户问法变了、知识库过期。没有更新机制的产品，退化是静默的——你不会收到报错，只会发现用量慢慢掉下去。这一张卡是所有面试里「你的项目上线后怎么维护」的标准答案。
四种载体：先挑成本最低的那个
载体改什么生效速度风险什么时候用
知识检索库、文档、FAQ分钟级低答案里的事实过时 / 缺失
指令system prompt、skill 文件、few-shot小时级中行为不对：该拒答没拒、格式不稳、该调工具没调
程序工具实现、校验、编排代码天级（要发版）中高能力缺失：需要新的动作、新的确定性约束
参数微调 / 蒸馏周级高以上都试过仍不够，且有 ≥ 数千条高质量样本
判据：能写进知识就不要改指令，能改指令就不要改代码

这是转型者最容易越级的地方——发现模型回答不好，第一反应是「要不要微调」。微调应该是最后手段：它最慢、最贵、最难回滚，而且一旦模型升级就要重做。面试里被问「你会不会微调」，正确答案不是「会」或「不会」，而是「我会先判断问题出在知识、指令还是能力层，只有前者都排除了才考虑」。

证据与指令隔离：别把一次失败当规则

从失败轨迹里学到的东西不能直接写进 system prompt。几条失败可能是同一个偶发原因，直接写成规则会污染指令、影响其他场景。正确做法是三级升格：

# 三级升格：轨迹 → 候选经验 → 指令
# 1. 原始证据：失败轨迹 id + 归因（留在库里，不进 prompt）
# 2. 候选经验：必须由 ≥3 条独立轨迹支撑，写成一句话假设
# 3. 指令：候选经验跑过 eval 确认不伤害其他场景，才能进 prompt

CANDIDATES = [
    {
        "id": "cand-007",
        "hypothesis": "用户问退款时，先查订单状态再回答，否则会给出不适用的政策",
        "evidence": ["trace-1832", "trace-1904", "trace-2011"],   # ≥3 条独立证据
        "eval_delta": +0.06,                                        # 进 prompt 前的实测增量
        "status": "promoted",                                       # candidate → promoted
    },
]
灰度与回滚：三段放量，一键退回
"""src/agentlab/rollout.py — prompt 版本化 + 稳定分流"""
from __future__ import annotations

import hashlib

PROMPTS = {
    "v3": "你是……（当前全量版本）",
    "v4": "你是……（候选版本：加了订单状态前置检查）",
}

# 放量计划：改了先只给 5%，看指标再往上加
ROLLOUT = {"v3": 95, "v4": 5}


def pick(user_id: str) -> str:
    """同一个用户必须稳定落在同一版本，否则指标会被抖动污染。"""
    bucket = int(hashlib.sha256(user_id.encode()).hexdigest()[:8], 16) % 100
    acc = 0
    for ver, weight in ROLLOUT.items():
        acc += weight
        if bucket < acc:
            return ver
    return "v3"


def rollback() -> None:
    """回滚必须是一行：把候选版本的权重置 0，不需要发版。"""
    ROLLOUT["v4"] = 0
    ROLLOUT["v3"] = 100
产物src/agentlab/rollout.py + notes/evolution.md：一条真实改进的完整记录（轨迹证据 → 候选经验 → eval 验证 → 灰度 → 全量或回滚）
验收 走完一次完整升级并留下四个证据：① 支撑改动的至少 3 条失败轨迹 id；② 改动前后的 eval 对比（20 题 × 3 次，含 Pass@5 与 Pass^5）；③ 灰度 5% 时的指标截图（成功率、P95 延迟、成本三项）；④ 真的回滚一次并把回滚耗时记下来。没做过回滚演练的回滚等于没有回滚——第一次执行回滚不该发生在出事的时候。
卡住怎么办
  • 没有真实用户，没法灰度：用两批不同的 eval 题集模拟——A 集调参、B 集验证，B 集只在最后跑一次。这也叫留出集，面试讲得通。
  • 找不到 3 条独立证据：说明这个「规律」还不够格进指令。把它留在候选库，等更多轨迹。
  • 灰度上来指标就掉：先看是不是分流不均匀（同一批用户被反复切换，体验断裂）。用户级稳定分流就是为了防这个。
  • 模型升级后全盘失效：所有 prompt 都要重跑 eval。这也是为什么缓存 prompt 版本、保留 eval 集比优化 prompt 更重要。

5闭卷自测

Q1–Q6 P5 阶段验收自测（点开看答题要点） 25min
Q1 为什么「流式」不只是体验问题，还是成本问题？

要点：流式让用户可在中途停止，避免为不需要的长回答付费；同时首字快意味着可以用更大的 max_tokens 而不担心等待；反过来，非流式必须等完整生成，超时就白花钱。

Q2 生成式 UI 的风险是什么？什么场景不该用？

要点：风险是不确定性（渲染错形态）、成本（多一次结构化输出调用）、可测性差（难断言）。不该用于：精确表单、固定高频任务、金额展示、强审计场景。

Q3 多租户 RAG 里，权限在哪一层做？为什么不能「检索完再过滤」？

要点：必须在检索 SQL 的 WHERE 里做。检索完再过滤的问题是：前 10 条可能全被过滤掉，用户看到「没找到」而实际有权限的文档排在第 30 位；另外无权限内容进了上下文就有泄露风险。

Q4 你的产品如果用户量涨 100 倍，第一个崩的是哪里？

要点：要给出具体判断，通常是「每次问答的模型调用成本」或「embedding 服务并发」。加分项：说出缓冲方案（缓存相同问题、批处理 embedding、把生成式 UI 的多余调用改成按需触发）。

Q5 你的 README 里为什么写「一条误答」？不会减分吗？

要点：不减分反而加分——它证明你做了评测且敢公开。招聘方最怕的是「不知道自己不知道」。关键是配套写清「已定位原因 + 下一步」。

Q6 首字延迟 4 秒，但用户反馈「还好」，你要不要优化？

要点：先确认「还好」是不是因为等待期间有可见反馈。如果是，说明感知管理有效，可以把优化优先级降低；但如果 p95 很差，长尾用户会流失。判断依据是数据不是感觉。

阶段通关条件

① 有公开可访问的链接且手机能打开；② 工具调用过程在界面上可见；③ 首字 p50 <1.5s；④ 超额请求被拒且提示友好；⑤ 成本看板能报出今日花费；⑥ README 六块齐全，陌生人 3 分钟能复述。
