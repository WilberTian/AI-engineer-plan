先明确一件事

24 周只是默认值，不是承诺。它按每周 10–12 小时算（工作日 5 天 × 45 分钟 + 周六 5 小时 + 周日 2 小时，合计约 10.75h）。你实际能给多少时间，用下面的换算表调整，别硬撑——把阶段拉长一倍，也比压缩内容学个大概强。

进入 P0 →

唯一会让你失败的坑

不是难度，是顺序。绝大多数人从「看 LangGraph 教程 / 看 LangChain 文档」开始，两周后能跑 demo 但说不清任何一层为什么这么设计，然后卡在原地。这份计划的顺序是反的：先手写，再用框架；先有 eval，再调 prompt；先能复现故障，再谈优化。按顺序走，慢就是快。

想知道行业里现在有哪些 harness？可以先看，但别急着装

2怎么用这份手册

规则只有三条，但违反任何一条这套计划就失效。

规则一

一次只开一张任务卡

每张卡标注了预计时长（30 分钟到 5 小时）。开始前只展开这一张，别把整页摊开读——读完全部会产生「我已经学会了」的错觉，而实际上一行代码没写。

规则二

每张卡必须留下产物

每张卡都有「产物」一栏。没有产物 = 没做。产物是文件、是命令输出、是一段能贴进 README 的结论。计划里所有验收都检查产物，不检查你「感觉懂了」。

规则三

卡住先看「卡住怎么办」

每张卡最后一段是我预判你会撞上的坑。先照那三条排查；还不行，把报错原文 + 你已排除的可能贴给 AI——这比问「为什么不工作」快十倍。

一页阶段页固定五段，顺序就是使用顺序

① 目标与交付物 → ② 本阶段该看什么（材料，一周一行）→ ③ 开始之前：要懂的 N 个概念（原理，动手前立住心智模型）→ ④ 任务卡（动手，卡内还有「关键知识点」）→ ⑤ 闭卷自测（答不上来就回第 ③ 段）。第 ③ 段的表写着「概念 / 一句话它是什么 / 为什么这样设计 / 落在哪张卡」，作用是让第 ④ 段不再是照抄——每张卡都能对回一个概念。

所有阶段页的任务卡都是同一套结构，看到就懂：

你已经有几年工程经验，看得懂代码。但「读懂」和「能改」是两件事。这些骨架故意留了不完整的地方（比如 agent loop 的停止条件只写了一个、eval 的 judge 只给了 prompt 没给解析），因为面试追问的正是这些空白处。抄完能跑不算过，能回答「如果我把这里改成 X 会怎样」才算过。

为什么这么切：三条依据

依据一

按依赖链切，不按技术清单切

「Python → RAG → Agent → 评测 → 部署」是技术清单，学完不知道自己能做什么。这里每一阶段都以前一阶段的产物为起点：没有 loop.py，P2 的检索器就没地方挂；没有评测集，P3 的改造就说不清是变好还是变坏。

依据二

按失败模式升级，一级治一种病

跑不起来（P1）→ 跑不准（P2）→ 跑不稳（P3）→ 跑不起（P4）→ 没人用（P5）。真实的 agent 项目就是按这个顺序死的，所以学习顺序和它对齐：遇到哪类失败，就知道该回哪个阶段补。P6 不在这条轴上——前五级说的是系统会怎么崩，P6 验证的是另一件事：这一整套能不能替你换到面试。

依据三

每阶段必须有可验收产物

没产物就不进下一阶段。这条是硬的：产物是文件、是命令输出、是能贴进 README 的结论。所有验收都查产物，不查「感觉懂了」。也正因为如此，附录不占周次——它不产生产物，不构成阶段。

参考层什么时候看：只有三个时刻

主线是路线图，参考层是字典——凡是能挂在「哪一步用」上的内容都已经搬进那一步了，留在参考层的只有「必须放在一起才有用」的，以及「查而不是学」的。所以它不需要被通读，只在三个时刻打开：

① 任务卡里写着「去查 X」——照卡片推进时卡在某个具体工具上；② 要做横向对比——P3 决定读哪个 harness 源码、P5 决定技术选型；③ 面试前 30 分钟——扫一遍术语表，把说法校准。

它没有「完成」这个状态

参考层不产生任何产物。如果你发现自己一整周都在读资源库、没碰任务卡，那就是走偏了——「这周该看什么」已经写在阶段页顶部，你不需要回来查。

七阶段 ≠ 七件作品

你只需要交付三个作品（见「你要交付的三个作品」），它们横跨三个阶段：RAG 问答服务在 P2 成型、Agent 任务执行器在 P3–P4 变可靠、生成式界面在 P5 上线。不用每个阶段都造一个新东西出来。

4先选靶心：7 种岗定去向，9 个方向定短板

「Agent 工程师」不是一种岗，是一类岗。同一个你，投不同细分，匹配度能差一档以上。这一步只花 10 分钟，但它决定后面 24 周的内容优先级会不会来回摇摆。

选靶心的结论

主攻「AI 产品工程师 / AI 全栈」，并行「AI 应用工程师」，用「Agent 工程」的深度做面试差异化。逻辑是：前者让你的前端经验变成溢价而不是负债，后者保证岗位池足够大、不至于卡死在一个细分上。这三类正好对应 P0-1 让你只挑的三类岗位——不是随便挑的，是匹配度算出来的。

一句话定义你的工作

「模型是一个有怪脾气的依赖，你的工作是围绕它做工程。」它不确定、按 token 收费、延迟以秒计、会自信地编造。所以真正难的部分全是你熟悉的东西：设计接口、管理状态、处理部分失败、控制成本、把评测嵌进流水线、调试分布式行为。区别只有一条——控制流由模型决定，而不是由你的代码决定。这也是为什么可观测性在这个岗位不是加分项，而是基础设施。

九个技术方向：靶心 = 岗位 × 你的短板

上一张表回答「投给谁」，这一张回答「你得会什么」。两件事合起来才叫靶心——只选岗位、不认短板，学时就会全程凭感觉分配时间。下面每个方向都配了一个诊断问题：能当场讲清并报出数字的算会，只能讲概念或者答不上来的算不会。

这张表怎么用：三次校准，不是随时查

它的价值不在绝对值，在变化量。同一张表用三次，每次 10 分钟，其余时间不要打开它：

  • Day 0（开始前，就现在）——只用来决定哪些卡精读、哪些卡快过。不要据此改周次：此刻还没动手，打分必偏。
  • W09 末（P2 完、作品 1 交付后）——同一张表再打一次，看哪块涨了。没涨但你花了很多时间的那块 = 方法问题，不是内容问题，停下来改方法，别加时间。
  • W17 末（P4 完、进 P5 前）——这时剩下的差距就是面试会暴露的差距，决定 P6 怎么包装。

还有第四次，不在这张表上：面试里被问住的那个问题指向哪个方向，那才是真短板。前三次是自评，第四次是市场给你的评分。

5你要交付的三个作品

招聘方读的是代码，不是你的简历。一个干净 README + 一套评测 + 一个能点的 demo，胜过十个「跑通过的 notebook」。2–3 个做透的项目，永远大于 10 个表面项目。

先说不做什么

不要做「10 个教程 demo」，也不要用「上传 PDF 问问题」这种通用主题——看不出你的领域判断，面试官已经看过几百个了。三个项目分别对应 P2、P3、P5，做完就是一套完整的证据链。

PROJECT 01 · P2（3–4 周）

带评测的领域问答系统

要证明：RAG 工程能力 + 评测纪律。这是「入场券」项目，没有它后面的项目不成立。

硬性要求

  • 真实语料 ≥ 500 页，别用玩具数据，带权限或租户维度
  • 混合检索 + 重排 + 引用（每条答案能点回原文段落）
  • 30 条以上测试集，分「检索组」「生成组」，出一张指标表
  • 一次「优化前后」对比：改了什么、指标怎么动、代价是什么
  • 一条命令跑评测并输出报告

不要做：只报一个总分（必须分组）、用通用 PDF 问答当主题。

PROJECT 02 · P3（4 周）

可复用的 Agent Harness

要证明：运行时理解 + 失败工程。在本地 learn-claude-code / claw0 基础上改造，不要从零抄。

硬性要求

  • 会话与任务状态可持久化，支持中断 / 恢复
  • 权限分层 + 危险动作审批（用代码强制，不靠 prompt）
  • 上下文压缩策略，且能说清「什么必须保留」
  • 完整 trace：每步工具调用的输入、输出、耗时、token
  • 一份故障注入报告：5 类故障的复现、表现、修复
  • 至少一个 MCP server 作为外部工具接入

关键动作：读完源码后删掉一半，写下为什么删——「为什么删」比代码本身更能证明你懂了。

PROJECT 03 · P5（3–4 周）

全栈 AI 产品（差异化杀手锏）

要证明：产品化 + 前端优势 + 交付能力。这个项目决定你能进什么档次的团队。

硬性要求

  • 公开可访问的链接，不需要别人本地跑
  • 流式输出 + 工具过程可见 + 可中断 + 可重试
  • 至少一个生成式 UI 场景：模型返回结构，界面动态渲染
  • 成本看板：每次请求的 token 与费用，日 / 周汇总
  • 失败率与 p95 延迟可见
  • 限额与滥用保护（否则别人一点就烧你的钱）

选题：选你自己真的会用的东西——真实使用会产生真实 bad case，而 bad case 是面试里最好的素材。

三个仓库的 README 统一按「六块结构」写（一句话 / 在线地址 / 关键数字 / 架构图 / 取舍说明 / 诚实局限），模板和示例数字见 P5-11。

7时间预算与换算

先算你真实能给的时间，再决定用哪一档。不要用「理想情况」估——按你过去一个月实际能挤出的时长算。

卡面上的估时加起来只有约 156.5 小时，不是 258 小时

84 张卡的「预计时长」合计约 156.5h，摊到 24 周是每周 6.5h；而默认档给的是每周 10.75h。差额不是空的，它要留给这几件事：① 照着卡做失败之后的重来（这是绝大多数时间的去向）；② P3 读 harness 源码；③ 写 README、写 notes、补学习笔记；④ 需要从零查资料时的额外阅读。
判断标准：如果你每周卡都在平均线内一次通过，说明你可以把周期压到 18 周；如果每周都在返工，10.75h 可能还不够。

8四个里程碑

每到一个节点做一次硬检查。不过关就不往前推——带病前进会在 P4 集中爆发。

1
W05 末 · 能证明「我的 agent 变好了」 判据：改一句 prompt，eval 通过率从 X% 变成 Y%，你能解释哪几条 case 翻转了、为什么。做不到说明 eval 是假的（测的是格式不是能力）。
2
W09 末 · 能分开报「检索错」和「生成错」 判据：随便给一条失败 case，你能在 5 分钟内判定是没检索到、检索到了但排序靠后、还是检索对了但模型没用。三种情况对应三种修法，判错就会改错地方。
3
W17 末 · 敢让别人用 判据：拔网线、限流、返回脏数据、进程被杀，四种情况系统都不静默失败，且报错信息能让人知道下一步做什么。加上一份能算出钱的花费表。
4
W24 末 · 材料能换到面试 判据：投 20 家拿到 ≥3 个技术面。拿不到不是运气问题，是简历/作品集的问题，回 W22 重做而不是加大投递量。
