先明确一件事

24 周只是默认值，不是承诺。它按每周 10–12 小时算（工作日 4 天 × 30–45 分钟 + 周六 4–5 小时 + 周日 2 小时）。你实际能给多少时间，用下面的换算表调整，别硬撑——把阶段拉长一倍，也比压缩内容学个大概强。

1怎么用这份手册

规则只有三条，但违反任何一条这套计划就失效。

规则一

一次只开一张任务卡

每张卡标注了预计时长（30 分钟到 5 小时）。开始前只展开这一张，别把整页摊开读——读完全部会产生「我已经学会了」的错觉，而实际上一行代码没写。

规则二

每张卡必须留下产物

每张卡都有「产物」一栏。没有产物 = 没做。产物是文件、是命令输出、是一段能贴进 README 的结论。计划里所有验收都检查产物，不检查你「感觉懂了」。

规则三

卡住先看「卡住怎么办」

每张卡最后一段是我预判你会撞上的坑。先照那三条排查；还不行，把报错原文 + 你已排除的可能贴给 AI——这比问「为什么不工作」快十倍。

一张任务卡的信息结构

所有阶段页的任务卡都是同一套结构，看到就懂：

区块含义怎么用
为什么这一步在整个岗位能力里的位置，以及不做它会缺什么30 秒读完，决定要不要认真做
怎么做有序步骤，带命令、代码骨架、参数选择理由照着敲，命令可直接复制
产物落在哪个文件 / 哪个表 / 哪个仓库做完立刻确认文件存在
验收可执行的检查，不是主观判断不过验收就别进下一张卡
卡住怎么办最常见的 3 个失败点 + 排查顺序先自查，再问 AI
为什么代码都给了还要自己敲

你已经有十年工程经验，看得懂代码。但「读懂」和「能改」是两件事。这些骨架故意留了不完整的地方（比如 agent loop 的停止条件只写了一个、eval 的 judge 只给了 prompt 没给解析），因为面试追问的正是这些空白处。抄完能跑不算过，能回答「如果我把这里改成 X 会怎样」才算过。

「Agent 工程师」不是一种岗，是一类岗。同一个你，投不同细分，匹配度能差一档以上。这一步只花 10 分钟，但它决定后面 24 周的内容优先级会不会来回摇摆。

选靶心的结论

主攻「AI 产品工程师 / AI 全栈」，并行「AI 应用工程师」，用「Agent 工程」的深度做面试差异化。逻辑是：前者让你的前端经验变成溢价而不是负债，后者保证岗位池足够大、不至于卡死在一个细分上。这三类正好对应 P0-1 让你只挑的三类岗位——不是随便挑的，是匹配度算出来的。

一句话定义你的工作

「模型是一个有怪脾气的依赖，你的工作是围绕它做工程。」它不确定、按 token 收费、延迟以秒计、会自信地编造。所以真正难的部分全是你熟悉的东西：设计接口、管理状态、处理部分失败、控制成本、把评测嵌进流水线、调试分布式行为。区别只有一条——控制流由模型决定，而不是由你的代码决定。这也是为什么可观测性在这个岗位不是加分项，而是基础设施。

3你要交付的三个作品

招聘方读的是代码，不是你的简历。一个干净 README + 一套评测 + 一个能点的 demo，胜过十个「跑通过的 notebook」。2–3 个做透的项目，永远大于 10 个表面项目。

先说不做什么

不要做「10 个教程 demo」，也不要用「上传 PDF 问问题」这种通用主题——看不出你的领域判断，面试官已经看过几百个了。三个项目分别对应 P2、P3、P5，做完就是一套完整的证据链。

PROJECT 01 · P2（3–4 周）

带评测的领域问答系统

要证明：RAG 工程能力 + 评测纪律。这是「入场券」项目，没有它后面的项目不成立。

硬性要求

  • 真实语料 ≥ 500 页，别用玩具数据，带权限或租户维度
  • 混合检索 + 重排 + 引用（每条答案能点回原文段落）
  • 30 条以上测试集，分「检索组」「生成组」，出一张指标表
  • 一次「优化前后」对比：改了什么、指标怎么动、代价是什么
  • 一条命令跑评测并输出报告

不要做：只报一个总分（必须分组）、用通用 PDF 问答当主题。

PROJECT 02 · P3（4 周）

可复用的 Agent Harness

要证明：运行时理解 + 失败工程。在本地 learn-claude-code / claw0 基础上改造，不要从零抄。

硬性要求

  • 会话与任务状态可持久化，支持中断 / 恢复
  • 权限分层 + 危险动作审批（用代码强制，不靠 prompt）
  • 上下文压缩策略，且能说清「什么必须保留」
  • 完整 trace：每步工具调用的输入、输出、耗时、token
  • 一份故障注入报告：5 类故障的复现、表现、修复
  • 至少一个 MCP server 作为外部工具接入

关键动作：读完源码后删掉一半，写下为什么删——「为什么删」比代码本身更能证明你懂了。

PROJECT 03 · P5（3–4 周）

全栈 AI 产品（差异化杀手锏）

要证明：产品化 + 前端优势 + 交付能力。这个项目决定你能进什么档次的团队。

硬性要求

  • 公开可访问的链接，不需要别人本地跑
  • 流式输出 + 工具过程可见 + 可中断 + 可重试
  • 至少一个生成式 UI 场景：模型返回结构，界面动态渲染
  • 成本看板：每次请求的 token 与费用，日 / 周汇总
  • 失败率与 p95 延迟可见
  • 限额与滥用保护（否则别人一点就烧你的钱）

选题：选你自己真的会用的东西——真实使用会产生真实 bad case，而 bad case 是面试里最好的素材。

三个仓库的 README 统一按「六块结构」写（一句话 / 在线地址 / 关键数字 / 架构图 / 取舍说明 / 诚实局限），模板和示例数字见 P5-11。

6四个里程碑

每到一个节点做一次硬检查。不过关就不往前推——带病前进会在 P4 集中爆发。

1
W05 末 · 能证明「我的 agent 变好了」 判据：改一句 prompt，eval 通过率从 X% 变成 Y%，你能解释哪几条 case 翻转了、为什么。做不到说明 eval 是假的（测的是格式不是能力）。
2
W09 末 · 能分开报「检索错」和「生成错」 判据：随便给一条失败 case，你能在 5 分钟内判定是没检索到、检索到了但排序靠后、还是检索对了但模型没用。三种情况对应三种修法，判错就会改错地方。
3
W17 末 · 敢让别人用 判据：拔网线、限流、返回脏数据、进程被杀，四种情况系统都不静默失败，且报错信息能让人知道下一步做什么。加上一份能算出钱的花费表。
4
W24 末 · 材料能换到面试 判据：投 20 家拿到 ≥3 个技术面。拿不到不是运气问题，是简历/作品集的问题，回 W22 重做而不是加大投递量。

8七个坑（都会真实发生）

这七条不是抽象警告，是这类转型里反复出现的具体失败方式。卡住的时候回来看一眼，比继续硬撑有用。

#坑表现怎么破
1把 demo 当作品拖拽平台搭个问答，页面能跑就以为会了。面试一问「多轮去重、任务拆失败重试、会话切换状态丢失」当场失语每个项目必须能回答「它在什么情况下会坏」
2框架观光LangChain / LangGraph / CrewAI / AutoGen 都跑过 hello world，一个都讲不清取舍深 1 个 + 能对比 3 个的适用边界，比 6 个都会强。想先看清全景再挑，读 Harness 与框架地图
3躲 Python只用 TS，读不了源码，只能看二手文章逼自己用 Python 重写一遍核心项目。痛苦两周，之后看什么都通（见 P1）
4简历自我降级写「转型」「零基础」「自学中」翻译经验，不否定经验——P6-1 有专门的翻译对照表
5不做评测 最致命「感觉比之前好多了」——没有任何数字哪怕 10 条测试集也比 0 条强；这是唯一能证明你「像工程师而不像玩家」的东西
6只学不做看了 40 小时课程，一行代码没提交每周必须有 commit：每天交出一个能留下痕迹的东西
7无视后端短板并发、限流、多租户、库表设计一问就虚在 P5 专门补，并且把「多租户 + 限额」真做进项目里

唯一会让你失败的坑

不是难度，是顺序。绝大多数人从「看 LangGraph 教程 / 看 LangChain 文档」开始，两周后能跑 demo 但说不清任何一层为什么这么设计，然后卡在原地。这份计划的顺序是反的：先手写，再用框架；先有 eval，再调 prompt；先能复现故障，再谈优化。按顺序走，慢就是快。
