W10读懂 harness：先把「为什么需要」搞清楚

第 10 周 · 这一周不写新功能，只做一件事：把每节代码和自己的 P1 实现对照，找出「它多做了什么、为什么值得做」。

P3-1 读源码的四步法（每节 30 分钟，别用别的方式） 本周通用
为什么：直接读代码会「看懂每一行但不知道它在解决什么」。四步法是反过来的：先跑出行为，再回头找实现。这样你记住的是「问题 → 方案」，不是「代码长什么样」。
步动作时长产出
1跑起来。按 README 跑通这一节，观察它比上一节多了什么行为（比如 s03 会问你「允许执行这个命令吗」）5min一句话：「这节新加的行为是 ___」
2画调用图。纸笔或文本框，画出「用户输入 → … → 输出」经过哪几个函数。不许看代码画，看行为画，然后再对着代码修正10min一张 6–10 个框的图
3找到最小改动。和上一节的 code.py 做 diff（diff s02_tool_use/code.py s03_permission/code.py），看它加了哪几行。added lines 通常不超过 30 行10min「核心是这 N 行，因为 ___」
4回答三个问题：解决了什么故障？代价是什么？什么时候不该用？5min三句话进 notes/harness.md
笔记模板（每节一段，照抄格式）
### s03_permission
- 解决什么故障：模型自己决定执行 `rm -rf`，没有拦截点
- 怎么实现：在 tool dispatch 前插一个 check，返回 (allow, reason)
- 代价：每个工具都要声明风险等级；用户会被频繁打断
- 什么时候不该用：纯只读工具集（查天气、查文档），加了只是噪音
- 和我 P1 的 loop 差在哪：我的 loop 直接调用 tool.fn()，没有前置检查点
产物notes/harness.md，每节一段五行
验收每一节的「代价」和「什么时候不该用」都写了。只写「解决了什么」= 没读懂——因为任何设计都有代价，说不出代价说明你在背。
卡住怎么办
  • 「跑不起来」：看 requirements.txt，用 uv pip install -r requirements.txt 到一个独立 venv。别污染 agentlab 的环境。
  • 「改不动，一改就崩」：这正是第 3 步的价值。先只读 diff，不改代码。等 W12 你要自己实现时才改自己的。
  • 「代码风格不熟，看得很慢」：这节代码量通常 100–300 行。设个 30 分钟闹钟，到点就写你已经理解的部分，剩下的标记「待回看」，别陷进去。

为什么：这三节你已经在 P1 手写过了。所以重点不是学，是比对差异——差异处就是你没考虑到的地方，也是最容易被面试问倒的地方。

节它在做什么我的 P1 实现差异说明什么
s01_agent_loop while + stop_reason 的最小循环 loop.py 的 for + 三个停止条件 我用 for range(max_steps)，它用 while + 显式 stop_reason。后者更容易在「模型主动停止 / 达到上限 / 被中断」之间区分——这个区分在持久化时很关键

s03 的一个关键设计，值得单独想 5 分钟

权限检查放在工具执行前，而不是放在 prompt 里说「不要执行危险操作」。区别是：prompt 是建议（模型可以不听），代码是强制（不听就跑不下去）。凡是有外部副作用的动作，规则必须写在代码里。这句话在 P4 的安全部分还会出现，现在先记住。

P3-3 s04–s06：hooks / todo / subagent 周日 2h
为什么：这三节对应三种「不改变循环结构但改变能力」的扩展方式。理解它们，你就理解了为什么成熟的 harness 是「一个小核心 + 一堆钩子」，而不是「一个大而全的循环」。
节解决什么实现要点代价 / 何时不该用
s04_hooks 在固定时机插入外部逻辑（工具调用前/后、会话开始/结束），不用改主循环 定义事件名 + 注册回调 + 按顺序执行；回调能拿到上下文、能阻断 钩子之间有隐式顺序依赖，多了就很难排查「到底谁改的」；纯内部脚本不需要
s05_todo_write 让 agent 显式维护待办，长任务不丢步骤 一个 todo_write 工具 + 强制在 system prompt 里要求先写待办；状态存在会话里 短任务（<3 步）加了只是噪音；待办本身会占上下文
s06_subagent 把「翻找大量信息」这种脏活隔离到独立上下文，只把结论带回主线程 子 agent 有独立 messages 数组和独立预算；返回结构化摘要而非全文 子 agent 看不到主线程上下文，容易重复劳动；调试变成两层，trace 必须能串起来
动手：给 subagent 做一个「上下文节省」测量

这是最容易被忽略但最能体现工程判断的实验：

# 场景：让 agent 在 20 个文件里找某个配置项
# A 方案：主 agent 逐个 read_file（20 次工具调用，结果全进主上下文）
# B 方案：主 agent 派一个 subagent，subagent 内部读 20 个文件，只回一句结论

# 记录三个数：
# 1. 主线程最终 prompt_tokens（决定成本和后续每轮延迟）
# 2. 总调用次数（决定总耗时）
# 3. 结论正确性

预期结果：B 方案主线程 token 少很多（可能只有 1/10），但总调用次数和耗时可能更高。这个权衡就是「subagent 什么时候值得用」的答案。

产物notes/harness.md 里 s04–s06 三段 + subagent 测量数据
验收能回答「什么任务该拆 subagent，什么不该」。判据应该是「子任务的信息量是否远大于它的结论」——是就拆，不是就别拆。
卡住怎么办
  • 不想实现 subagent：这周只要求读懂，不要求实现。W12 也不做 subagent（那是 P4 之后的事）。把测量做成「纸面推算」也可以——但要算出具体 token 数。
  • hooks 看不出价值：想一个具体需求——「每次工具调用都记一条审计日志，但不想改工具实现」，这就是 hooks 的典型场景。

W11上下文、记忆、错误恢复

第 11 周 · 这一周的主题是「长任务为什么活不下来」。四个原因：上下文爆了、忘了关键约束、出错了不会绕、任务状态没地方存。

P3-4 s07–s09：skill 加载 / 上下文压缩 / 记忆 周六 2.5h
为什么：s08（compact）是整个仓库最值钱的一节。所有长任务 agent 都绕不开「上下文总会满」这个物理事实，而压缩策略的选择直接决定「长任务能不能不迷失」。
节解决什么实现要点关键判断
s07_skill_loading 能力按需加载，而不是全塞进 system prompt 先只给「技能名 + 一句话描述」，模型认为需要时才加载完整内容 什么时候该拆成技能：内容超过 ~2000 token 且不是每次都用
s08_context_compact 接近窗口上限时压缩历史 触发阈值（如 80%）→ 保留最近 N 轮 + 摘要旧轮 → 拼接；摘要要保留约束/结论/待办 压缩会丢信息，一定要丢得可控。哪些不能丢见下
s09_memory 跨会话保留用户偏好和项目事实 抽取 → 存储（文件/DB）→ 检索 → 注入；写入要有触发条件和去重 记忆是「全局上下文污染」的高发区：写错一条会影响之后所有会话
读 s08 时重点看这四行逻辑

不用看全部代码，找到这四个决策点就够了：

  1. 触发条件：按 token 数还是按轮数？按 token 更准，但需要每次都统计。
  2. 保留什么：通常保留最近 K 轮原文 + 系统提示 + 第一条用户消息（原始目标最容易被压丢）。
  3. 摘要用什么模型：用同一个贵模型是浪费，用小模型可能丢关键细节。多数人用便宜的。
  4. 压缩后怎么衔接：直接替换？还是插入一条「以下是之前对话的摘要」？后者模型更容易接上。
产物notes/harness.md 里 s07–s09 三段，s08 那段要写清上面四个决策点各自的做法
验收能说出「压缩时绝对不能丢的四样东西」（用户约束、已确认结论、未完成待办、失败过的路径）。
卡住怎么办
  • 「压缩逻辑看不懂」：先只读 README（中文的），读懂「什么时候压、压掉什么」，代码里找对应的 if 和字符串拼接就行。
  • 「memory 那节太长」：只看「写入条件」和「检索方式」两个函数。其余跳过。
P3-5 s10–s12：system prompt 组装 / 错误恢复 / 任务系统 周日 2h
为什么：s10 会让你重新审视自己的 SYSTEM 常量——你可能一直是「想一句加一句」，而成熟的做法是分层组装。s11 则直接对应 P4 的容错设计。
节要点对你的直接用处
s10_system_prompt 分层组装：身份 → 能力边界 → 工具使用规则 → 输出格式 → 当前环境信息（动态） 把 P1 的 SYSTEM 常量改成函数：build_system(ctx)，动态部分（时间、可用工具、用户偏好）在运行时注入
s11_error_recovery 错误分类 → 可重试/需改参数/需上报；重试要带退避和上限；错误要压缩后回灌 P4 的故障注入会用这套分类。现在先对照你的 loop 缺哪几层
s12_task_system 多步骤任务的状态机：pending / in_progress / done / blocked，支持依赖 直接决定 W12 的 checkpoint schema 该怎么设计

"""src/agentlab/prompt.py — 分层组装，替代 loop.py 里的 SYSTEM 常量"""
from __future__ import annotations

from datetime import datetime
from pathlib import Path

IDENTITY = "你是一个可以使用工具的助手，服务于个人工程知识库。"

BOUNDARIES = """能力边界：
- 只能访问 data/ 和 notes/ 目录下的文件
- 不能执行 shell 命令、不能修改文件
- 不知道的信息就说不知道，不要推测
"""

TOOL_RULES = """工具使用规则：
1. 需要外部信息时才调用，能直接回答就直接回答
2. 一次可以调多个，但不要重复查同一件事
3. 工具报错时先读懂错误，再决定改参数还是放弃
4. 最多 6 次工具调用，信息足够就立刻给答案
"""

OUTPUT = """输出要求：
- 直接回答，不描述思考过程
- 引用文件时写出文件名
- 不确定的部分明确标注「不确定」
"""


def build_system(extra: str = "") -> str:
    now = datetime.now().strftime("%Y-%m-%d %H:%M")
    files = len(list(Path("data/corpus").glob("*.md")))
    dynamic = f"""当前环境：
- 时间：{now}
- 语料文件数：{files}
"""
    parts = [IDENTITY, BOUNDARIES, TOOL_RULES, OUTPUT, dynamic]
    if extra:
        parts.append(f"本次任务补充说明：\n{extra}")
    return "\n\n".join(p.strip() for p in parts if p.strip())

  • 动态内容破坏了缓存：这是真实代价。正确做法是动态部分放最后，且尽量稳定（比如只精确到天，不精确到秒）。
P3-6 产出一张「压缩策略对照表」（面试可直接用） 周日 1h
为什么：上下文管理是 2026 年 AI 工程师最核心的手艺之一。能讲清四种压缩策略的适用场景和代价，比会用一个框架值钱。
策略怎么做保真度成本适用失效场景
滑动窗口只保留最近 N 轮，旧的直接丢低零闲聊、无长程依赖任务目标在第一条消息里（一丢就迷失）
摘要压缩用小模型把旧轮压成要点中一次额外调用长对话、需要保留脉络需要精确原文（法条、代码、数字）
结构化抽取把历史抽成 {目标, 约束, 已完成, 待办, 失败路径}中高一次额外调用 + schema 维护多步骤任务、agent 长跑对话型场景（抽取会丢掉语气和上下文）
外置检索历史存起来，需要时再检索回来高（按需）存储 + 检索延迟超长会话、可回溯的工作记录需要「一直在眼前」的信息（当前任务状态）

加一栏「组合用法」，这才是真实答案：

典型生产组合 = 结构化抽取管任务状态 + 摘要压缩管对话脉络 + 外置检索管历史细节 + 滑动窗口兜底最近 3 轮原文。单一策略都不够。

产物notes/context-strategies.md：上面这张表 + 你的组合方案 + 一次实测（压缩前后任务完成率对比）
验收能回答「压缩后任务失败率上升，你怎么定位是哪部分信息丢了」——方法：对比压缩前后的抽取结果，看哪个字段缺失；再针对那条 case 做最小复现。

W12持久化、中断恢复、人工审批

第 12 周 · 这一周把 agent 从「一个进程」变成「一个有状态的服务」。做完你就能回答「你的 agent 跑到一半机器挂了会怎样」。

P3-7 checkpoint + resume：kill -9 之后能接着跑 周六 3h
为什么：长任务的现实是「一定会被打断」——部署、超时、用户关闭页面、机器重启。没有 checkpoint 的 agent 每次都从头开始，等于每次都烧一遍钱。
三张表，别设计得更复杂
CREATE TABLE IF NOT EXISTS runs (
  run_id      text PRIMARY KEY,
  task        text NOT NULL,
  status      text NOT NULL,          -- running | awaiting_approval | done | failed | aborted
  step_idx    integer NOT NULL DEFAULT 0,
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS run_messages (
  run_id      text NOT NULL REFERENCES runs(run_id) ON DELETE CASCADE,
  seq         integer NOT NULL,
  payload     jsonb NOT NULL,          -- 原样存一条 message
  PRIMARY KEY (run_id, seq)
);

CREATE TABLE IF NOT EXISTS approvals (
  id          bigserial PRIMARY KEY,
  run_id      text NOT NULL REFERENCES runs(run_id) ON DELETE CASCADE,
  step_idx    integer NOT NULL,
  tool_name   text NOT NULL,
  args        jsonb NOT NULL,
  decision    text,                    -- NULL=待定 | allow | deny
  decided_at  timestamptz,
  UNIQUE (run_id, step_idx)
);

为什么 run_messages 存原始的 message 数组而不是「状态摘要」？因为 prompt 缓存和上下文重建都要求消息字节级一致。摘要会让恢复后的行为和中断前不同，这种「看起来恢复了但结果变了」的 bug 极难查。

"""src/agentlab/runtime/store.py（节选）"""
from __future__ import annotations

import json
from typing import Any

import psycopg

DSN = "postgresql://postgres:devpass@localhost:5432/agentlab"


def save_run(run_id: str, task: str, status: str, step_idx: int) -> None:
    with psycopg.connect(DSN) as conn, conn.cursor() as cur:
        cur.execute(
            """INSERT INTO runs (run_id, task, status, step_idx)
               VALUES (%s,%s,%s,%s)
               ON CONFLICT (run_id) DO UPDATE
                 SET status = EXCLUDED.status,
                     step_idx = EXCLUDED.step_idx,
                     updated_at = now()""",
            (run_id, task, status, step_idx),
        )
        conn.commit()

               ON CONFLICT (run_id, seq) DO NOTHING""",
            [(run_id, start_seq + i, json.dumps(m, ensure_ascii=False))
             for i, m in enumerate(messages)],
        )
        conn.commit()


def load_run(run_id: str) -> tuple[str, str, int, list[dict[str, Any]]]:
    with psycopg.connect(DSN) as conn, conn.cursor() as cur:
        cur.execute("SELECT task, status, step_idx FROM runs WHERE run_id=%s", (run_id,))
        task, status, step_idx = cur.fetchone()
        cur.execute(
            "SELECT payload FROM run_messages WHERE run_id=%s ORDER BY seq", (run_id,)
        )
        messages = [json.loads(r[0]) for r in cur.fetchall()]
    return task, status, step_idx, messages

然后在 loop.py 里每轮做两件事：（1） 追加新消息后立即落盘；（2） 更新 step_idx。顺序很重要：先落盘再执行下一步，否则崩在中间会丢消息。

"""src/agentlab/runtime/approval.py"""
from __future__ import annotations

import json

import psycopg

DSN = "postgresql://postgres:devpass@localhost:5432/agentlab"

# 按工具名 + 参数特征判断风险。不要只看工具名 —— 同一个工具可能安全也可能危险。
DANGEROUS_PATTERNS = {
    "write_file": lambda a: True,
    "delete_file": lambda a: True,
    "send_message": lambda a: True,
    "run_sql": lambda a: not a.get("sql", "").strip().lower().startswith("select"),
    "fetch_url": lambda a: True,          # 出网就该确认，防止数据外泄
}


def needs_approval(tool_name: str, args: dict) -> bool:
    rule = DANGEROUS_PATTERNS.get(tool_name)
    return bool(rule and rule(args))


def request(run_id: str, step_idx: int, tool_name: str, args: dict) -> str:
    """登记待审批，返回 'pending'。调用方据此中断整个 run。"""
    with psycopg.connect(DSN) as conn, conn.cursor() as cur:
        cur.execute(
            """INSERT INTO approvals (run_id, step_idx, tool_name, args)
               VALUES (%s,%s,%s,%s)
               ON CONFLICT (run_id, step_idx) DO NOTHING""",
            (run_id, step_idx, tool_name, json.dumps(args, ensure_ascii=False)),
        )
        conn.commit()
    return "pending"


def get_decision(run_id: str, step_idx: int) -> str | None:
    with psycopg.connect(DSN) as conn, conn.cursor() as cur:
        cur.execute(
            "SELECT decision FROM approvals WHERE run_id=%s AND step_idx=%s",
            (run_id, step_idx),
        )
        row = cur.fetchone()
    return row[0] if row else None

三个容易做错的地方

写之前先知道：MCP 在 2026-07 做了一次大改

你现在能搜到的 MCP 教程，绝大多数写的是 2025-11-25 那一版——有 initialize 握手、有 Mcp-Session-Id。而 2026-07-28 的规范把这些都删了：协议核心改成无状态，版本和能力走每个请求的 _meta，网关靠 Mcp-Method / Mcp-Name 头路由，列表结果带 ttlMs 可缓存，Tasks 和 MCP Apps 变成扩展，Roots / Sampling / Logging 进入弃用（12 个月移除窗口）。

对你的直接影响：几乎没有。你这张卡写的是 stdio 传输的本地 server，不走 Streamable HTTP，照原样写就行。唯一的动作是——写完之后读一遍官方 changelog，确认自己知道无状态改了什么。为什么值得花这 20 分钟：面试问「MCP 架构」时，说出「2026 年改成无状态核了，所以能放普通负载均衡后面」，比背「MCP 是客户端-服务端协议」值钱得多。完整对照表见 Harness 地图 §4。

"""src/agentlab/mcp_server.py — 把 RAG 检索暴露成 MCP 工具"""
from __future__ import annotations

from mcp.server.fastmcp import FastMCP

from agentlab.rag.retrieve import hybrid_retrieve   # P2 的实现

mcp = FastMCP("agentlab-kb")


@mcp.tool()
def search_knowledge(query: str, top_k: int = 5) -> str:
    """在个人工程知识库中检索。

    适合回答「文档里怎么写的」「某个配置项是什么」类问题。
    返回带编号和来源文件名的片段；没有命中时会明确说明。
    """
    chunks = hybrid_retrieve(query, top_k=top_k)
    if not chunks:
        return f"知识库中没有与「{query}」相关的内容。"
    return "\n\n".join(
        f"[{i}] ({c.source}) {c.text[:600]}" for i, c in enumerate(chunks, 1)
    )


@mcp.tool()
def list_documents() -> str:
    """列出知识库中的所有文档名。用户问「你有哪些资料」时使用。"""
    from pathlib import Path

    files = sorted(p.name for p in Path("data/corpus").glob("*.md"))
    return f"共 {len(files)} 个文档：\n" + "\n".join(f"- {f}" for f in files)


@mcp.resource("kb://stats")
def stats() -> str:
    """知识库统计信息（只读资源，不是工具）。"""
    import psycopg

    with psycopg.connect("postgresql://postgres:devpass@localhost:5432/agentlab") as conn:
        with conn.cursor() as cur:
            cur.execute("SELECT count(*), count(DISTINCT doc_id) FROM chunks")
            n, d = cur.fetchone()
    return f"chunks={n}, documents={d}"


if __name__ == "__main__":
    # stdio：给本地客户端用（Claude Desktop / Cursor / Claude Code）
    # 如果要给别人远程连，改成 transport="streamable-http" 并加鉴权
    mcp.run(transport="stdio")

"""src/agentlab/tools_mcp.py — 把 MCP server 的工具适配进 Registry"""
from __future__ import annotations

import asyncio
import json

from mcp import ClientSession
from mcp.client.stdio import stdio_client

from agentlab.tools import Registry, Tool, ToolResult


def load_mcp_tools(command: list[str], prefix: str = "kb") -> Registry:
    """连接一个 stdio MCP server，把它的工具包装成同步 Tool。

    注意：这里用 asyncio.run 简化了实现。生产环境应该把整个 agent 改成 async，
    而不是在每个工具里起一个事件循环。
    """
    registry = Registry()

    async def _load() -> list[tuple[str, str, dict]]:
        async with stdio_client(command) as (read, write):
            async with ClientSession(read, write) as session:
                await session.initialize()
                listed = await session.list_tools()
                return [(t.name, t.description or "", t.inputSchema) for t in listed.tools]

    for name, desc, schema in asyncio.run(_load()):
        def make(tool_name: str):
            def call(**kwargs) -> ToolResult:
                async def _call() -> ToolResult:
                    async with stdio_client(command) as (read, write):
                        async with ClientSession(read, write) as session:
                            await session.initialize()
                            res = await session.call_tool(tool_name, kwargs)
                            text = "\n".join(
                                c.text for c in res.content if hasattr(c, "text")
                            )
                            return ToolResult(ok=not res.isError, content=text)

                return asyncio.run(_call())

            return call

        registry.register(Tool(
            name=f"{prefix}_{name}",
            description=desc,
            parameters=schema,
            fn=make(name),
        ))
    return registry

"""src/agentlab/observability.py"""
from __future__ import annotations

import os
from contextlib import contextmanager

from langfuse import Langfuse, observe

langfuse = Langfuse(
    public_key=os.getenv("LANGFUSE_PUBLIC_KEY", ""),
    secret_key=os.getenv("LANGFUSE_SECRET_KEY", ""),
    host=os.getenv("LANGFUSE_HOST", "http://localhost:3000"),
)


@contextmanager
def trace_run(run_id: str, task: str):
    """一次任务 = 一个 trace，每个 step = 一个 span。"""
    with observe(name="agent_run", as_type="span") as span:
        span.update(input={"task": task}, metadata={"run_id": run_id})
        yield span


def log_step(name: str, payload: dict, usage: dict | None = None) -> None:
    """手工打点：工具调用、上下文大小、token 用量。"""
    langfuse.create_event(name=name, metadata=payload)
    if usage:
        # 让成本列有数：必须把 usage 报给 Langfuse
        langfuse.update_current_generation(usage_details=usage)

5闭卷自测

Q1–Q7 P3 阶段验收自测（点开看答题要点） 30min
Q1 workflow 和 agent 的分界线在哪？给一个「看起来像 agent 但应该做成 workflow」的例子。

要点：分界线是「下一步走哪由谁决定」——由代码决定是 workflow，由模型决定是 agent。例子：客服工单分类 + 按类别走不同处理流程，看似需要 agent，实际分类后每条路径都是固定的，做成 workflow 更稳更便宜。

Q2「工具太多」为什么会降低准确率？你怎么判断该拆还是该合？

要点：工具越多，description 之间的边界越模糊，模型在「选哪个」上的决策空间变大、出错概率上升；同时工具定义本身占上下文。判断方法：如果两个工具在 80% 的情况下都会被考虑，说明它们该合并或该拆清边界。可操作判据：把工具数从 12 降到 6 跑一遍 eval，看准确率变化。

Q3 什么规则必须写进代码（hook / deny）而不是写进 prompt？为什么？

要点：凡是有不可逆副作用或合规要求的——删数据、转账、发外部消息、访问越权数据。原因是 prompt 是概率性约束（模型可能不听、可能被注入绕过），代码是确定性约束。

Q4 长任务跨多个上下文窗口时，怎么让新会话快速接上？

要点：把状态外置成结构化记录（目标 / 约束 / 已完成 / 待办 / 失败路径），新会话先读这份记录再开工；而不是靠「摘要整段对话」。补充：文件系统本身也是上下文——把进展写进 progress.md，新会话读它，比塞进 prompt 更可控。

Q5 MCP 是什么？它解决了什么「不用它就很难受」的问题？

要点：工具/数据的标准协议，让一个 server 被所有客户端复用。不用它的话，每换一个客户端（Claude Desktop / Cursor / 自己的 agent）就要重写一遍工具适配层，N×M 的工作量。

Q6 你的 checkpoint 存了什么？为什么不存「状态摘要」而存原始 messages？

要点：存 runs（任务/状态/步数）+ run_messages（原始消息）+ approvals。存原始消息是因为恢复后的行为必须和中断前一致，摘要会导致模型看到不同的上下文、做出不同决策，且破坏 prompt 缓存。

Q7 审批被拒绝后，为什么不应该直接终止任务？

要点：「被拒绝」是一条有价值的信息，回灌给模型它常能找到替代路径（比如不能写文件就输出到对话里）。直接终止会让用户体验成「半途而废」，而且浪费了前面的工作。

阶段通关条件

① kill -9 之后能恢复并跑完；② 危险工具触发时真的挂起等人；③ 外部客户端能调你的 MCP 工具；④ trace 里能看到 5 个以上 span 且带 token 数；⑤ Q1–Q7 至少答对 5 题。
