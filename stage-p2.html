开始之前：这一阶段要懂的 11 个概念

这一页不只有动手。下面每张卡都会用到这几个心智模型——概念先立住，命令才不是照抄；概念没立住，改一行代码就不知道会牵动哪里。

概念一句话它是什么为什么这样设计 / 关键约束落在哪张卡
分块是检索精度的上限块切错了，后面的 embedding、rerank、prompt 全都救不回来检索只能返回“已经存在的块”；边界切错的答案永远补不回来，这是唯一一个必须在第一步就做对的环节P2-1 · P2-3
结构感知分块按标题切，并把标题路径拼进块文本，让每块自带上下文否则“该值”“它的上限”这类指代脱离标题就无法解析；检索到了，模型也答不对P2-2 · P2-3
稠密 vs 稀疏embedding 管语义相近，BM25 管词面精确，两者的失败方式正好相反向量检索对专有名词、型号、错误码几乎必漏——这就是要混合检索的全部理由P2-6
recall@k 是唯一硬指标前 k 条里有没有正确文档，直接决定生成侧的天花板没进前 5 的文档，再好的 prompt 也生成不出来；先量召回，再谈别的，顺序不能反P2-5
RRF 用排名不用分数两路检索的分数不同量纲，只能按名次融合加权平均要先归一化两路分数、还要调权重，换语料就得重调；RRF 只看名次，不需要归一化P2-7
rerank 是贵但准的第二层cross-encoder 把 query 和文档拼一起过一遍模型，只对 20–30 条候选做它对全库做不起（成本与延迟都是 O(N)），只能当精排用；候选超过 50 条时 CPU 上单次要几秒，得先砍候选P2-8
拒答要两层检索侧阈值（最高分低于阈值直接拒）+ 生成侧指令（资料不足就说不知道）只靠 prompt 不可靠，只靠阈值会误杀可答问题；两层缺一层都有洞P2-10
权限必须在检索前过滤把租户/文档权限写进查询条件，而不是检索出 10 条再筛掉没权限的先检索后过滤，会让“有权限的文档一条都没进前 10”，模型于是拒答或者编造P2-11
引用让答案可验证每句结论挂回原文块，能点击回原文没有引用，「答案对不对」只能靠感觉；面试问「怎么证明它没编」，答的就是引用和拒答这两层P2-9
记忆要分三层轨迹（流水账，按时间追加、只增不改）· 用户长期记忆（档案，会被反复改写和淘汰）· 业务状态（任务阶段），三者生命周期完全不同混成一层就出问题：把轨迹当记忆存，检索被历史噪音淹没；把记忆当轨迹存，用户改主意了就没法更新——档案必须能改，流水账不能P2-17
记忆格式按价值分档Simple Notes → Enhanced Notes → JSON Cards → Advanced JSON Cards，粒度和成本逐级上升关键且少量的事实（人物关系、健康约束）值得用最贵的格式保证查得准；大量非关键的事实必须用最便宜的压住成本。全用一种，必然在某一头吃亏P2-17
RAG 最贵的错误：先调 prompt

90% 的人遇到「答得不对」就开始改 prompt、换模型。而真实原因分布大概是：切分边界错 40%、元数据缺失 20%、检索召回不足 20%、排序差 10%、prompt 问题 10%。改 prompt 最多碰到最后那 10%。所以本周第一件事不是写检索，是造一把能区分这五种的尺子。

"""scripts/parse_docs.py — PDF/HTML → markdown，失败回退纯文本"""
from __future__ import annotations

import json
import time
from pathlib import Path

from docling.document_converter import DocumentConverter

RAW = Path("data/raw")
OUT = Path("data/corpus")
REPORT = Path("data/parse_report.json")


def main() -> None:
    OUT.mkdir(parents=True, exist_ok=True)
    conv = DocumentConverter()
    report = []

    for src in sorted(RAW.iterdir()):
        if src.suffix.lower() not in {".pdf", ".html", ".htm", ".docx"}:
            continue
        t0 = time.perf_counter()
        entry = {"file": src.name, "ok": False, "chars": 0, "ms": 0, "backend": "docling"}
        try:
            result = conv.convert(str(src))
            md = result.document.export_to_markdown()
            # 关键：加一行元信息头，后面分块时能带上来源
            md = f"<!-- source: {src.name} -->\n\n{md}"
            (OUT / f"{src.stem}.md").write_text(md, encoding="utf-8")
            entry.update(ok=True, chars=len(md))
        except Exception as exc:  # noqa: BLE001
            # 回退：至少把文本捞出来，别整个流程卡住
            try:
                if src.suffix.lower() == ".pdf":
                    from pypdf import PdfReader

                    text = "\n\n".join(p.extract_text() or "" for p in PdfReader(src).pages)
                    (OUT / f"{src.stem}.md").write_text(
                        f"<!-- source: {src.name} (fallback) -->\n\n{text}", encoding="utf-8")
                    entry.update(ok=True, chars=len(text), backend="pypdf")
                else:
                    entry["error"] = f"{type(exc).__name__}: {exc}"
            except Exception as exc2:  # noqa: BLE001
                entry["error"] = f"docling: {exc}; fallback: {exc2}"
        entry["ms"] = round((time.perf_counter() - t0) * 1000)
        report.append(entry)
        print(f"{'OK ' if entry['ok'] else 'ERR'} {src.name:<32} {entry['chars']:>7} chars  {entry['ms']:>6}ms  {entry['backend']}")

    REPORT.write_text(json.dumps(report, ensure_ascii=False, indent=2), encoding="utf-8")
    ok = sum(1 for r in report if r["ok"])
    print(f"\n{ok}/{len(report)} 成功")
    print(f"平均 {sum(r['chars'] for r in report) // max(ok,1)} 字符/文件")


if __name__ == "__main__":
    main()

P2-3 三种分块策略对比（用同一套 query 量出来） 周六 2h
为什么：这是 P2 最有面试价值的一张卡。别人说「我用了语义分块」，你说「我对比了三种，在 20 条 query 上 recall@5 分别是 0.55 / 0.70 / 0.65，结构感知最好但不是因为它更聪明，是因为它保留了标题上下文」——这是两个层级的回答。
关键知识点

检索只能返回已经存在的块，所以分块决定检索的上限。 如果答案正好跨在两个块的边界上，两块各自都不完整，谁都排不进前 5——这不是 rerank 能救的，也不是换个更大的模型能救的。这是全流程里唯一一个「第一步没做对，后面全白费」的环节。

  • 三种策略的差别在「按什么边界切」：固定长度按 token 数切（简单，容易切断句子和表格）；按段落/语义切（尊重作者结构，长度不均）；结构感知按标题切（最贵最准，尤其适合技术文档）。
  • 判断标准不是「哪种更好」，是在同一批 query 上量 recall@5。同一个 embedding 模型、同样的 20 条 query，只换切法。这一步不做，后面所有优化都没有基线。
  • 块必须带定位信息：文档 id + 标题路径 + 块序号。否则引用点不回原文（P2-9），拒答也说不清依据。
三种策略，固定变量
策略实现预期优预期劣
固定长度每 400 token 一块，重叠 15%块大小均匀，embedding 输入稳定切断句子、丢掉标题、表格被拆散
递归字符按 \n\n → \n → 句号 → 空格 逐级切，到上限停不切断段落，实现简单长章节内仍然会盲目切
结构感知按 markdown 标题切，超长再按 token 二次切，并把标题路径拼进块文本每块自带上下文，符合人类查阅习惯依赖解析质量；块大小差异大

"""src/agentlab/rag/chunk.py"""
from __future__ import annotations

import re
from dataclasses import dataclass
from pathlib import Path

from chonkie import RecursiveChunker, TokenChunker


@dataclass
class Chunk:
    id: str
    text: str
    source: str
    section: str = ""
    strategy: str = ""


# 三种策略不是「哪个更好」，而是三档对照：fixed 是基线，recursive 是通用解，
# structural 是有结构文档的最优解。先让三档都能跑，再让 measure_recall 说话。
def fixed(path: Path, size: int = 400, overlap: int = 64) -> list[Chunk]:
    chunker = TokenChunker(chunk_size=size, chunk_overlap=overlap)
    return [
        Chunk(id=f"{path.stem}#f{i}", text=c.text, source=path.name, strategy="fixed")
        for i, c in enumerate(chunker.chunk(path.read_text(encoding="utf-8")))
    ]


# recursive 不认标题，只按分隔符优先级往下试（段落 → 句子 → 词）。
# 好处是任何文本都能切，坏处是永远切不出一个语义完整的「小节」。
def recursive(path: Path) -> list[Chunk]:
    chunker = RecursiveChunker(chunk_size=400)
    return [
        Chunk(id=f"{path.stem}#r{i}", text=c.text, source=path.name, strategy="recursive")
        for i, c in enumerate(chunker.chunk(path.read_text(encoding="utf-8")))
    ]


# 结构性切分的前提：标题层级本身就是天然的语义边界
H2 = re.compile(r"^(#{1,4})\s+(.+)$", re.M)


def structural(path: Path, max_tokens: int = 400) -> list[Chunk]:
    """按标题切，超长再用段落二次切。关键：块文本前面拼上标题路径。"""
    text = path.read_text(encoding="utf-8")
    lines = text.splitlines()
    sections: list[tuple[list[str], list[str]]] = []  # (标题路径, 正文行)
    stack: list[tuple[int, str]] = []
    buf: list[str] = []

    def flush() -> None:
        if buf and any(l.strip() for l in buf):
            sections.append(([t for _, t in stack], buf.copy()))
        buf.clear()

    for line in lines:
        m = H2.match(line)
        if m:
            flush()
            level = len(m.group(1))
            while stack and stack[-1][0] >= level:
                stack.pop()
            stack.append((level, m.group(2).strip()))
        else:
            buf.append(line)
    flush()

    out: list[Chunk] = []
    for path_titles, body in sections:
        prefix = " > ".join(path_titles)
        body_text = "\n".join(body).strip()
        if not body_text:
            continue
        # 粗略按 1 token ≈ 1.6 中文字符 估算，超长就按段落再切
        pieces = (
            [body_text]
            if len(body_text) <= int(max_tokens * 1.6)
            else _split_paragraph(body_text, int(max_tokens * 1.6))
        )
        for j, piece in enumerate(pieces):
            # 关键：把标题路径拼回块文本（下面那句 text=）。
            # 不拼的话，「默认端口是 8080」这块脱离标题后，模型不知道在说哪台设备。
            out.append(Chunk(
                id=f"{path.stem}#s{len(out)}",
                text=f"【{prefix}】\n{piece}" if prefix else piece,
                source=path.name,
                section=prefix,
                strategy="structural",
            ))
    return out


# 二次切分只按段落累积，不再往句子里切：宁可超一点，也别把一个条件句劈成两半
def _split_paragraph(text: str, limit: int) -> list[str]:
    paras = [p for p in text.split("\n\n") if p.strip()]
    out: list[str] = []
    cur = ""
    for p in paras:
        if len(cur) + len(p) <= limit:
            cur += ("\n\n" if cur else "") + p
        else:
            if cur:
                out.append(cur)
            cur = p[:limit]
    if cur:
        out.append(cur)
    return out


# 统一入口：三种策略一个名字对外。P2-4 的 ingest.py 和后面 P3-9 要用的 retrieve
# 都调这一个函数——别在调用方写 if strategy == "fixed"，
# 那等于把同一份分派逻辑复制到每个调用处，加第四种策略时要改的地方就散了。
STRATEGIES = {"fixed": fixed, "recursive": recursive, "structural": structural}


def chunk_file(path: Path, strategy: str = "structural") -> list[Chunk]:
    # 早失败比晚失败好：拼错策略名如果在几百个文件之后才炸，
    # 你会分不清这是数据问题还是代码问题。
    if strategy not in STRATEGIES:
        raise ValueError(f"未知策略 {strategy!r}，可选：{sorted(STRATEGIES)}")
    return STRATEGIES[strategy](path)
产物src/agentlab/rag/chunk.py：三个策略函数 + 统一入口 chunk_file(path, strategy)（P2-4 的 ingest、后面所有调用都走这一个名字）+ 一份对比表（chunk 数 / 平均字符 / 后续填 recall）
验收三种策略各自的 chunk 数、平均长度打印出来；structural 的每条 chunk 文本开头能看到 【标题 > 子标题】。
卡住怎么办

关键知识点

代码写错可以改，schema 错了要重跑全部 embedding。 所以表结构要在第一版就定对：块文本、向量、文档 id、标题路径、块序号、权限字段，一个都不能少。返工成本不是改几行代码，是重新解析 + 重新向量化整份语料。

  • 为什么存标题路径而不是只存文档 id：检索时「这块属于哪一节」是判断相关性的重要线索，生成时它又是引用的锚点。存下来比事后 join 便宜得多。

from pathlib import Path

import psycopg
from pgvector.psycopg import register_vector
from sentence_transformers import SentenceTransformer

recall@k 和 MRR 分别说明什么

recall@5：正确片段有没有进前 5。它衡量「检索有没有找到」——这是生成质量的上限，找不到就一定答不对。MRR：正确片段排在第几位的倒数平均。它衡量「排序好不好」——排第 1 得 1 分，第 5 得 0.2 分。两个都低说明检索烂；recall 高但 MRR 低说明「找到了但没排前面」，这时候加重排最有效。

第 7 周 · 三件套的标准形状：召回要宽（多路并行）、融合要稳（RRF）、排序要准（cross-encoder）。

P2-6 关键词检索：为什么向量检索一定会漏掉专有名词 周六 1.5h
为什么：embedding 把语义压成向量，副作用是罕见字符串被平滑掉。产品型号「XR-2000B」、函数名「useSyncExternalStore」、错误码「E1024」，向量检索经常找不准；而这些恰恰是用户最常精确查的东西。
关键知识点

两种检索的失败方式正好相反，这才是要混合的全部理由。 向量检索把文本压成稠密向量，语义相近的会靠近，代价是精确词面被稀释：产品型号 X200-Pro、错误码 ERR_4012 在向量空间里几乎没有区分度，经常漏。BM25 按词频打分，专有名词只要出现过就能命中，但同义词（「退款」vs「退钱」）完全无能为力。

  • 不是替代关系：一条 query 走两路，再融合（P2-7 的 RRF）。单路再调参也补不上另一路的洞。
  • 落地要有两个证据：① 只用向量时，那几条专有名词 query 确实失败；② 加上 BM25 后同一批 query 的 recall@5 提升。没有这两个数，「我做了混合检索」就是口号。
  • 一个常被忽略的细节：BM25 依赖分词。中文要先分词（jieba 之类），英文要处理连字符和大小写——型号 X200-Pro 被切成三个词之后，精确匹配就失效了。

        tok = tok.strip()
        if tok and tok not in {"，", "。", "、", "；", "：", "（", "）", "\n", " "}:

    return out

P2-7 RRF 融合：为什么不用加权平均 周六 1h
为什么：加权平均需要把两路分数归一化，而归一化方式会随分布变化失真（这次除 10、换个语料就要除 100）。RRF 只用排名，天然免疫量纲问题，几乎不需要调参——这就是它成为默认做法的原因。
"""src/agentlab/rag/fusion.py"""
from __future__ import annotations


# 融合的是「名次」不是「分数」：向量余弦分和 BM25 分不在一个量纲上，
# 直接加权平均是没有意义的，这是 RRF 存在的全部理由。
def rrf(
    rankings: list[list[str]],
    k: int = 60,
    weights: list[float] | None = None,
) -> list[tuple[str, float]]:
    """Reciprocal Rank Fusion。

    score(d) = Σ weight_i / (k + rank_i(d))，rank 从 1 开始。
    k 的作用是压低「第 1 名」的绝对优势：k 越大，排名差异被抹得越平。
    60 是原论文的经验值，一般不用改。
    """

    if weights is None:
        weights = [1.0] * len(rankings)
    scores: dict[str, float] = {}
    # 用 dict 累加：同一块被两路同时召回时分数叠加——这就是混合检索变准的机制
    for ranking, w in zip(rankings, weights, strict=True):
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + w / (k + rank)
    # 只返回 id 和分数，不带正文：融合层不该关心内容，取正文是下一步的事
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)

import time

import psycopg
from sentence_transformers import CrossEncoder

# 模型全局只加载一次：每次调用都重新 load 要 2–3 秒，比你省下的那点延迟贵得多
_model: CrossEncoder | None = None


def get_model() -> CrossEncoder:
    global _model
    if _model is None:
        # 中文/多语用 bge-reranker-v2-m3；英文可用 ms-marco-MiniLM-L-6-v2（更快）
        _model = CrossEncoder("BAAI/bge-reranker-v2-m3", max_length=512)

# cross-encoder 把 query 和文档一起送进模型，所以比向量相似度准，也慢一个数量级。
# 只能在候选 30 条这一层用，不能拿去全库搜。
def rerank(query: str, candidates: list[tuple[str, float]], top_k: int = 5):
    """candidates: [(chunk_id, 融合分)] → 返回重排后的 [(id, score)] + 耗时"""
    if not candidates:
        return [], 0.0
    ids = [c[0] for c in candidates]
    with psycopg.connect("postgresql://postgres:devpass@localhost:5432/agentlab") as conn:
        with conn.cursor() as cur:
            cur.execute("SELECT id, content FROM chunks WHERE id = ANY(%s)", (ids,))
            content = dict(cur.fetchall())
    pairs = [(query, content[i][:1200]) for i in ids if i in content]
    # 截到 1200 字：reranker 有 max_length，超长会被静默截断。主动截比被动截心里有数

    # 单独计 rerank 的耗时：它是这条链上最容易超出预算的一段（200–800ms 都算正常）
    t0 = time.perf_counter()
    scores = get_model().predict(pairs)
    ms = (time.perf_counter() - t0) * 1000

    ranked = sorted(zip([i for i in ids if i in content], scores),
                    key=lambda x: float(x[1]), reverse=True)
    return [(i, float(s)) for i, s in ranked[:top_k]], ms

"""src/agentlab/rag/retrieve.py — P2 检索管线的唯一对外入口"""
from __future__ import annotations

from dataclasses import dataclass

import psycopg
from pgvector.psycopg import register_vector
from sentence_transformers import SentenceTransformer

from agentlab.rag import bm25
from agentlab.rag.fusion import rrf
from agentlab.rag.rerank import rerank

DSN = "postgresql://postgres:devpass@localhost:5432/agentlab"
# 模型加载一次全局复用：每次检索都重新 load 等于多花 2–3 秒，和优化方向正好相反
_model = SentenceTransformer("BAAI/bge-m3")

# 三个阶段的宽度必须分开：召回 30 → 融合后取 10 → 重排完留 5 进 prompt。
# 候选池小于 20 时 RRF 基本没得发挥；大于 50 时延开始失控。
# 别把「候选数」和「最终条数」合成一个参数，那样你就没法单独调召回宽度了。
RECALL_K = 30
FUSE_K = 10


# 返回带字段的对象，而不是裸 tuple：下游要 source / section 做引用和溯源，
# 用 tuple 的话以后每加一个字段都得改所有调用处。
@dataclass
class Retrieved:
    id: str
    text: str
    source: str    # 文档标题，给用户看的出处
    section: str   # 标题路径，P2-9 引用的锚点
    score: float


def vector_search(query: str, k: int = RECALL_K, strategy: str = "structural",
                  tenant_id: str = "demo") -> list[str]:
    qv = _model.encode(query, normalize_embeddings=True)
    with psycopg.connect(DSN) as conn:
        register_vector(conn)
        with conn.cursor() as cur:
            # tenant 过滤写在 WHERE 里，而不是检索完在应用层筛：
            # HNSW 取满 k 条就停，应用层再筛会让「要 10 条」实际只剩 3 条。细节见 P2-11
            cur.execute(
                """SELECT id FROM chunks
                   WHERE strategy = %s AND tenant_id = %s
                   ORDER BY embedding <=> %s LIMIT %s""",
                (strategy, tenant_id, qv, k),
            )
            return [r[0] for r in cur.fetchall()]


def _fetch(ids: list[str], tenant_id: str) -> dict[str, tuple[str, str, str]]:
    # BM25 那一路用的是全库 pkl（索引里没有租户维度），所以最后这一道复核不能省：
    # 融合阶段完全可能把别的租户的块排进来，这里统一把门。
    if not ids:
        return {}
    with psycopg.connect(DSN) as conn, conn.cursor() as cur:
        cur.execute(
            """SELECT id, content, doc_title, section FROM chunks
               WHERE id = ANY(%s) AND tenant_id = %s""",
            (ids, tenant_id),
        )
        return {r[0]: (r[1], r[2], r[3] or "") for r in cur.fetchall()}


def hybrid_retrieve(query: str, top_k: int = 5, strategy: str = "structural",
                    tenant_id: str = "demo", use_rerank: bool = True) -> list[Retrieved]:
    """向量 + 关键词 → RRF → 可选重排 → 带溯源字段的 top_k 条。

    score 的口径要留意：开着重排时它是 cross-encoder 的 logits（不是 0–1），
    关掉重排时是 RRF 融合分（上限只有 1/(60+1)≈0.016）。
    所以 P2-10 定拒答阈值时必须单独去算未归一化的余弦相似度，
    不能拿这个字段去比 0.35——量纲根本不是一回事。
    """
    v = vector_search(query, RECALL_K, strategy, tenant_id)
    b = [i for i, _ in bm25.search(query, RECALL_K)]
    fused = rrf([v, b])[:FUSE_K]

    if use_rerank:
        order, _ms = rerank(query, fused, top_k)
    else:
        order = fused[:top_k]

    fetched = _fetch([i for i, _ in order], tenant_id)
    out: list[Retrieved] = []
    for cid, score in order:
        if cid not in fetched:      # 被租户过滤掉的块直接丢，不留占位
            continue
        text, source, section = fetched[cid]
        out.append(Retrieved(
            id=cid, text=text, source=source, section=section, score=float(score),
        ))
    return out
必须量三个数（不是两个）
指标怎么测期望
recall@5（重排前 vs 后）重排只改顺序不改集合，所以recall@5 可能变低（原本第 5 的被挤出）重点看 MRR 是否上升
MRR同上脚本换成重排后的顺序应该明显上升（0.45 → 0.65 量级）
P95 延迟对 20 条 query 记 20 次耗时，取 P95CPU 上重排 30 条候选约 200–800ms
什么情况下不该加重排

① 召回本来就低——重排救不了没检索到的东西，先修分块。
② 对话场景且预算紧——用户能感知 300ms 以上的额外等待，而 MRR 提升可能只体现在少数问题上。
③ 候选只有 5 条——重排的收益来自「从 30 条里挑 5 条」，候选太少就没得挑。

"""src/agentlab/rag/cite.py"""
from __future__ import annotations

import re
from dataclasses import dataclass

CITE = re.compile(r"\[(\d+)\]")


@dataclass
class CiteCheck:
    cited: list[int]
    invalid: list[int]            # 引用了不存在的编号
    uncited_sentences: list[str]  # 有结论但没标来源

    @property
    def ok(self) -> bool:
        return not self.invalid and len(self.uncited_sentences) <= 1


def check(answer: str, n_chunks: int) -> CiteCheck:
    cited = sorted({int(m) for m in CITE.findall(answer)})
    invalid = [c for c in cited if c < 1 or c > n_chunks]
    # 粗粒度：按句号/换行切，看哪些句子没带引用也不像「拒答」
    sentences = [s.strip() for s in re.split(r"[。\n]", answer) if len(s.strip()) > 15]
    uncited = [s for s in sentences if not CITE.search(s) and "资料中没有" not in s]
    return CiteCheck(cited=cited, invalid=invalid, uncited_sentences=uncited)

P2-11 权限过滤：必须在检索前做，不能在生成后做 周六 1h
为什么：这是企业 RAG 的第一道红线。很多人写成「先检索出 10 条，再过滤掉用户没权限的」——结果是有权限的文档可能一条都没进前 10，用户看到「没找到」，但真正的问题是过滤发生在太后面。更糟的是：如果过滤后的上下文里残留了无权限内容，模型可能把它说出来。
正确做法：过滤条件进 SQL
-- 错：先取 10 条再在应用层过滤
SELECT id, content FROM chunks ORDER BY embedding <=> %s LIMIT 10;

-- 对：tenant_id / 可见范围作为 WHERE 条件，参与查询
SELECT id, content FROM chunks
WHERE tenant_id = ANY(%s)              -- 用户可访问的租户/项目
  AND (visibility IS NULL OR visibility = 'public' OR owner_id = %s)
ORDER BY embedding <=> %s
LIMIT 10;
三个必须写进代码的规则
  1. 权限参数不能来自模型。它必须来自已认证的用户上下文（session），工具签名里不接受「tenant_id」这类由模型填的参数。
  2. 审计日志记「检索范围」而不只是「结果」。出问题时你要能回答「这次查询扫了哪些文档」。
  3. 做一次越权测试：用 A 租户的身份，问一个只有 B 租户文档能回答的问题，期望结果是拒答，而不是答出来。
第 4 条（最容易漏）：WHERE 写对了，HNSW 仍可能少给你结果

这是 pgvector 上最反直觉的一处，也是多租户 RAG 的第一事故源：HNSW 是近似索引，它先按向量距离取 hnsw.ef_search（默认 40）个候选，再对这批候选套 WHERE。如果 WHERE 筛掉了 90%，你能拿到的就只剩 4 条左右——SQL 不报错，只是安静地少返回。表面看是「检索效果变差」，实际是索引扫描顺序的问题，往 prompt 或分块上找原因会白费一周。

-- 判据：ef_search 要按「过滤后还剩多少」放大
--   ef_search ≥ 你要的条数 ÷ 预计通过过滤的比例
--   要 10 条、预计只有 25% 的块属于本租户 → ef_search ≥ 40
SET LOCAL hnsw.ef_search = 120;

-- pgvector 0.8.0+ 才有这个开关：让索引迭代扫描直到凑够 LIMIT，
-- 而不是扫完固定候选就交差。必须同时给一个上限，否则最坏情况会退化成全表扫。
SET LOCAL hnsw.iterative_scan = 'relaxed_order';
SET LOCAL hnsw.max_scan_tuples = 4000;

SELECT id, content FROM chunks
WHERE tenant_id = ANY(%s)
ORDER BY embedding <=> %s
LIMIT 10;

怎么确认自己踩到了这个坑：同一条 query，把 WHERE 去掉能返回 10 条、加上只剩 3 条——就是这个。反过来，ef_search 不是越大越好，它直接换召回质量以外的东西：扫描时间。调到够用就行，把「我按什么比例定的」写进注释。

产物带 tenant_id 过滤的检索函数（含 ef_search 的取值理由）+ 一次越权测试记录 + 一份「加/不加 WHERE 各返回几条」的对照
验收越权测试返回「资料中没有相关信息」；日志里能看到过滤条件。
卡住怎么办
  • 只有一份语料，没法测越权：造两个 tenant，各放 3 个文件，A 问只有 B 有的内容。
  • 过滤后结果太少：不是提高 LIMIT——LIMIT 只是从「已经被 WHERE 筛过」的那批里取，加大它拿不到更多。要调的是 hnsw.ef_search，或打开 iterative_scan（见上一节）。两个都调过仍然少，才说明是语料本身没覆盖。
P2-15 把检索包成工具：切在目标上，不切在接口上 周日 2h
为什么：P1 你写的工具只有一个假的天气查询，真实项目不会这么简单。最容易犯的错是把每个接口都包成一个工具——search_by_title、search_by_date、get_chunk、list_docs……工具一多，模型选错的概率立刻上升，公开评测里工具超过 100 个时最先进的模型也开始挑错。工具应该切在用户目标上，不是切在后端接口上。这一条在面试里几乎必问，因为它是「会写 agent」和「设计过 agent」的分界线。
先做减法：三个工具覆盖全部检索目标
工具覆盖什么目标不要拆成
search找资料。把标题、日期、来源、文档类型全收进 filters 参数search_by_title / search_by_date / search_by_source

from __future__ import annotations

from pydantic import BaseModel, Field

from agentlab.llm import LLM


# 两个 judge 判的是不同的事，不能合并：忠实度问「有没有编」，正确性问「对不对」。
# 一个高一个低时，要改的代码完全相反。
class Faithful(BaseModel):
    grounded: bool = Field(description="回答是否完全基于给定的引用块")
    unsupported: list[str] = Field(
        default_factory=list, description="超出资料的陈述，逐条摘出原文，没有则空"
    )


class Correct(BaseModel):
    passed: bool
    reason: str = Field(max_length=200)


def faithfulness(llm: LLM, answer: str, contexts: list[str]) -> Faithful:
    ctx = "\n\n".join(f"[{i}] {c}" for i, c in enumerate(contexts, 1))
    # 给每块编号再喂进去：模型才能说「第 2 条支持」，你才查得动它的理由
    return llm.structured([{"role": "user", "content": f"""资料：
{ctx}

回答：
{answer}

判断：回答里的每个事实性陈述，是否都能在资料中找到依据？
只评判依据，不评判语气、长度、是否好读。"""}, ], Faithful)


# 正确性判官必须给标准答案。不给 gold 的话，它就退化成「另一个模型觉得对不对」，
# 测的是模型口味，不是你的系统。
def correctness(llm: LLM, question: str, gold: str, answer: str) -> Correct:
    return llm.structured([{"role": "user", "content": f"""问题：{question}
标准答案：{gold}
系统回答：{answer}

判断系统回答与标准答案在事实上是否一致。表述方式不同不算错。
关键条件缺失、数值错误、因果关系反了，算错。"""}, ], Correct)
为什么忠实度和正确性要分开

一条回答可以完全忠于资料但答错了问题（资料本身过期），也可以答对了但与资料无关（模型本来就知道）。前者是数据问题，后者是幻觉风险。只有两个数分开看，才知道该修数据还是修 prompt。

第一个分裂：Pass@k 与 Pass^k

同一道题跑 5 次，单次成功率 p = 0.6 时：

指标算法数值它回答什么
Pass@51 − (1−p)⁵，任一次成功即算成功≈ 99%能力上限：这事它到底能不能做
Pass^5p⁵，连续 5 次都成功才算≈ 7.8%业务可靠性：它能不能一直做对
这两个数差 91 个百分点，但它们是同一个系统

演示、比赛、写 README 用 Pass@k；付款、退款、发信、改数据用 Pass^k。给系统定目标时如果只写「成功率 95%」，那这句话在工程上没有意义——必须写清是哪一个。这是面试里区分「跑过 demo」和「上过生产」的高频问题。

第二个分裂：失败要归因到「首个」错误

一条轨迹有 8 步，第 3 步检索拿错了文档，后面 5 步全在错误信息上打转。如果只记「最终答案错」，你会去调最终答案的 prompt，而真正的病灶在第 3 步。归因必须定位到首个错误步。

公开评测里有个数字值得记住：某客服基准 704 次运行、240 次失败，人工复盘后发现其中 80 次（三分之一）属于「环境状态改对了，但没告诉用户」——这类失败在总通过率里完全看不出来，只有逐条读轨迹才会暴露。所以归因不是可选步骤。

"""evals/metrics.py — 通过率之外，你还需要这几个数"""
from __future__ import annotations

import random
from dataclasses import dataclass, field


@dataclass
class Run:
    task_id: str
    ok: bool
    steps: list[dict] = field(default_factory=list)   # 每步：tool / args / result / error


# ---------- 1. 两种成功率 ----------
def pass_at_k(runs: dict[str, list[bool]], k: int) -> float:
    """任一次成功即算成功：能力上限。"""
    return sum(1 for rs in runs.values() if any(rs[:k])) / len(runs)


def pass_pow_k(runs: dict[str, list[bool]], k: int) -> float:
    """连续 k 次都成功才算：业务可靠性。"""
    return sum(1 for rs in runs.values() if len(rs) >= k and all(rs[:k])) / len(runs)


# ---------- 2. 失败归因：三步判据 ----------
def attribute(run: Run) -> str:
    """把一条失败轨迹归到第一个出问题的环节，不要归到「最终答案错」。"""
    for i, s in enumerate(run.steps):
        if s.get("error"):
            return f"step{i}:tool_error"          # 工具本身报错
        if s.get("tool") and not s.get("result"):
            return f"step{i}:bad_args"            # 参数错，工具没返回有效结果
    if not run.ok:
        return "final:answer_format"              # 步骤都对，答案表达不合格
    return "ok"


# ---------- 3. 显著性：小样本别用正态近似 ----------
def boot_ci(xs: list[float], n: int = 2000) -> tuple[float, float]:
    means = sorted(
        sum(random.choice(xs) for _ in xs) / len(xs) for _ in range(n)
    )
    return means[int(n * 0.025)], means[int(n * 0.975)]


def paired_delta(a: dict[str, bool], b: dict[str, bool]) -> tuple[int, int]:
    """只在 A 上对的题数、只在 B 上对的题数。两边都对/都错的不提供信息。"""
    a_only = sum(1 for t in a if a[t] and not b.get(t))
    b_only = sum(1 for t in b if b[t] and not a.get(t))
    return a_only, b_only
样本量不够就别下结论

配对比较里，a_only + b_only < 10 时差异基本是噪声——20 道题里 3 道变好、2 道变差，说明不了任何事。经验线：至少 20 题 × 3 次才敢说「有提升」，要写进简历就 ≥ 30 题 × 5 次。跑得慢就把并发开到 5，别用「样本少所以跑得快」自我安慰。

第三个分裂：验证器要同时证明「修好了」和「没修坏」

前面两个数都建立在一个默认前提上——你知道什么叫「通过」。这个前提在真实基准里是要专门设计的，而且它决定了通过率能不能被骗。

组定义证明什么只做这一组的后果
FAIL_TO_PASS改动前失败、改动后通过问题确实解决了agent 可以删掉碍事的断言蒙混过关
PASS_TO_PASS改动前后都通过没有引入新缺陷等于没检验——它天生就是过的

这个拆分来自 SWE-bench Verified 对「修复完成」的定义，后来成了代码类 agent 的通用做法。它还有一个副产品：能顺带筛出时好时坏的不稳定用例——一条 PASS_TO_PASS 反复摇摆，那是测试本身的问题，不是 agent 的问题，得先修测试。

你的 eval 集里其实已经有这两组的雏形：must_contain 那几条是 PASS_TO_PASS（改完不许坏），P1-12 的三条 should_fail 是 FAIL_TO_PASS（改完必须能拦住）。缺的是把它们分别算成一个数——现在只有一个总通过率，所以「修好两条」和「改坏两条」会互相抵消，你看不出来。

# ---------- 4. 验证器双层：分四态记，不合并成一个总数 ----------
def tally(cases: list[dict], before: dict[str, bool], after: dict[str, bool]) -> dict[str, int]:
    """原本对/现在对、原本错/现在对……四种状态分别计数。

    合并成总通过率会掩盖 regressed —— 它才是唯一需要立刻回滚的信号。
    """
    out = {"held": 0, "fixed": 0, "regressed": 0, "still_broken": 0}
    for c in cases:
        b, a = before[c["id"]], after[c["id"]]
        if b and a:
            out["held"] += 1           # PASS_TO_PASS 该守住的，守住了
        elif b and not a:
            out["regressed"] += 1      # 原本对、现在坏：优先级最高的报警
        elif a:
            out["fixed"] += 1          # FAIL_TO_PASS 该修好的，修好了
        else:
            out["still_broken"] += 1   # 还没轮到它，不算退步
    return out
第四个分裂：你改的东西，和你关心的东西，不是一回事

前面三条都在讲「怎么把数算准」。这一条更隐蔽——数算对了，但算的是错的东西。

机制指标 ≠ 目标指标

你直接动手改变的那个量叫机制指标；你真正希望变好的那个量叫目标指标。两者经常不是同一个，而且「机制改善了、目标反而变差」很常见。

书里那个例子值得记住：为了让 agent 更快，你把计划文件缩短了——计划长度是机制指标，确实降了；真正的目标是会话级成本，它涨了。因为计划不够详细，多出了几轮「编辑 → 检查 → 再编辑」的循环，总输出量反而更高。

所以每次做对比实验前先问一句：我改变的东西，和我真正关心的东西，是同一个吗？ 如果不是，以目标为准。

放到你这个项目上，这类错最容易出在三处：

  • 把「重排后 MRR 涨了」当成「答得更准了」——MRR 是机制，答案正确率才是目标。有些 query 重排后排序更好看，但把唯一正确的那篇挤出了 top-3，整体准确率反而掉。
  • 把「压缩后 token 少了」当成「成本降了」——压缩本身要额外调一次模型，压完可能还要重跑，账单未必更低。
  • 把「拒答率上升」当成「更严谨了」——要看拒掉的里面有多少是真不可答。拒答率是个机制指标，它的目标指标是「该答的答对、不该答的别瞎编」这两个数。

顺带配一组护栏指标：目标变好的同时，如果延迟、成本、拒答率里有任何一项明显变差，这次改动也不算成功。护栏是「不能变差的底线」，不是优化目标——它和机制指标的区别是：护栏不需要被改善，只需要不被击穿。W20 做消融时会真正用上这两类指标。

先分清三个「记得」

「记忆」这个词在 agent 里被用得很松，实际指三样东西，生命周期完全不同：

层是什么活多久
轨迹一次运行里的完整事件（用户消息、模型回复、工具结果），按时间追加、只增不改单次会话
用户长期记忆跨会话提炼出来的稳定信息，键值对绑在用户 ID 上，会被反复改写、合并、淘汰长期，跨会话
业务状态你自己定义的高层阶段：「需要澄清」「处理中」「等待付款」一个任务

一句话分开它们：轨迹是流水账，长期记忆是档案。流水账为了追溯和调试，只追加；档案为了使用，必须能被改写——用户改主意了，旧那条就得让位。你这张卡做的是第二层。

怎么算「记得好」：先定尺子再动手

记忆最容易做成「感觉挺智能」的东西，所以先立三层判据。三层是递进的，上一层过不了，下一层的分数没有意义：

层要求对照的例子
基础回忆用户直接给出的、结构化的、无歧义的信息，能精确存取「我的会员号是 12345」→ 三天后问起来能报出 12345，不是「大概是 1 万多」
多会话检索跨多个会话、多个对象，检索出全部相关信息并做判断「帮我约个保养」→ 用户有两辆车，得问是哪一辆，而不是随便挑一辆
主动服务没有指令，主动关联很久以前的信息做预警或整合订国际航班时联想到几个月前存的护照信息，发现快过期，主动提醒

第三层是「助理」和「工具」的分界线。你不需要做到第三层才算过，但要能说清自己做到第几层——面试里问「你的记忆做了多少」，答「能记住用户偏好」是模糊的，答「第一层 12 条用例全过，第二层 8 条里过了 5 条，第三层没做」是可信的。

存成什么样：四种格式，从便宜到贵
格式一条存成什么优势代价什么时候选
Simple Notes一个不可再分的最小事实读写 O(1)，最便宜关联全丢：「在 A 公司做推荐系统」被拆成三条独立事实，要综合才能答的问题得重新拼大量、非关键的对话事实
Enhanced Notes一段带完整上下文的叙述语义完整，人和模型都读得懂冗余；改一个属性要重写好几段需要叙述性理解的场景
JSON Cards类别 → 子类 → 键值，三层嵌套支持部分更新：改职位不影响公司名刚性分类：一件事同时属于三类时，塞进哪一格都丢信息结构清楚的事实（联系方式、偏好）
Advanced JSON Cards在 JSON Cards 上再加来源背景、主体、关系、时间戳能消歧：「张医生」可能是自己的牙医，也可能是父亲的心内科医生生成和维护最贵，每轮多一次调用关键且少量（人物关系、健康史）
选型只有一句判据

关键且少量的（人物关系、长期偏好、健康约束）用 Advanced JSON Cards，保证能准确检索；大量且非关键的（随口提过的行程、一次性的项目背景）用 Simple Notes，压住成本。生产系统两种一起用——同一个 agent 里不同类别的信息走不同路径，这不算不一致，这才是设计。

这张表说的是「存成什么形状」。P3-12 会从另一个角度看同一件事：写入代价（全量追加 → 摘要压缩 → 结构化抽取）。两者是同一个阶梯的两个面，不是两套分类——原文留存对应 Simple / Enhanced Notes，结构化抽取对应 JSON Cards。

实现：写入、改主意、按需注入
"""src/agentlab/memory.py — 抽取 → 存储 → 检索 → 注入"""
from __future__ import annotations

import json
from dataclasses import dataclass, asdict
from pathlib import Path


@dataclass
class Memory:
    key: str        # 稳定的键，如 personal.diet / family.father.doctor
    value: str      # 一句话就能独立读懂的事实
    kind: str       # preference / fact / todo
    source: str     # 哪次会话写进来的，出问题能回溯


def upsert(store: dict[str, Memory], m: Memory) -> str:
    """同一个键已存在时，覆盖还是并存——必须显式决定，别留给默认行为。"""
    old = store.get(m.key)
    if old is None:
        store[m.key] = m
        return "added"
    if old.value == m.value:
        return "noop"           # 重复写入不制造噪音
    store[m.key] = m            # 后写的覆盖先写的：用户改主意了
    return "updated"            # 单独计数，冲突率是记忆质量第一指标


def recall(store: dict[str, Memory], query: str, k: int = 5) -> str:
    """按需注入：只取相关的几条拼进本轮，不要全量塞进 system。

    这里用关键词匹配示意；上生产换成向量检索，复用 P2 的 embedder。
    """
    hits = [m for m in store.values() if any(w in m.value for w in query.split())]
    hits.sort(key=lambda m: m.kind != "preference")   # 偏好排在一般事实前面
    return "\n".join(f"- {m.value}" for m in hits[:k])


def load(path: Path) -> dict[str, Memory]:
    """启动时读一次。文件不存在就当新用户，这不是错误。"""
    if not path.exists():
        return {}
    raw = json.loads(path.read_text(encoding="utf-8"))
    return {k: Memory(**v) for k, v in raw.items()}


def save(path: Path, store: dict[str, Memory]) -> None:
    """每次 upsert 之后整份写回。这个量级够用，上量再换 SQLite。"""
    path.write_text(
        json.dumps({k: asdict(v) for k, v in store.items()}, ensure_ascii=False, indent=2),
        encoding="utf-8",
    )
抽取三原则：写什么比怎么写更重要

会话结束后要额外调一次模型去提炼。这次调用的产出必须同时满足三条，否则宁可不写：

  1. 选择性：丢掉短期细节。「搜索返回了 3 个选项」不该进记忆，「用户不吃辣」该进。
  2. 抽象化：把这一次的具体行为归纳成长期属性。「这次要了靠窗」→「偏好靠窗座位」。
  3. 结构化：用可检索的字段存，不要存一整段自由文本——否则冲突检测和过期处理都做不了。
三个最容易做错的地方
  • 把整段对话当记忆存。那不是记忆，只是换了个地方存历史。记忆的价值在于「提炼」，存原文只会让检索变差、成本变高。
  • 把记忆写进 system prompt。记忆内容每次会话都可能变，写进 system 就等于每轮换一个前缀，KV Cache 全灭。正确做法见 P3-12：记忆按需加载，拼在本轮用户消息前面。
  • 用进程内的 dict 验证「跨会话」。那不是跨会话，那是同一进程里的两个函数调用。真要测，得开两个进程、中间把状态落盘。

5闭卷自测

Q1–Q7 P2 阶段验收自测（点开看答题要点） 30min
Q1 「检索到了正确文档，但答案还是错」——按什么顺序排查？至少说出 4 个检查点。

要点：语料是否有 → 切分是否完整 → 是否进前 5 → 排名是否靠后 → 上下文是否被截断 → prompt 是否允许它自由发挥。按这个顺序，因为前面的成本低且影响面大。

Q2 什么时候该用纯关键词检索？什么时候纯向量就够？

要点：查专有名词、错误码、版本号、人名、精确短语时关键词不可替代；查「概念解释」「同义改写」类问题时向量更强。多数系统要混合，但只有 20 条测试集时你会发现混合的收益集中在少数精确查询上。

Q3 重排一定能提升质量吗？代价是什么？什么情况下不该加？

要点：只改顺序不改集合，所以 recall 可能下降、MRR 通常上升。代价是 200–800ms 延迟和一次模型推理成本。召回本身低的时候不该加（救不了），候选太少时不该加（没得挑）。

Q4 上下文腐化是什么？为什么「窗口有 1M 就能塞 1M」是错的？

要点：塞得越多，关键信息被淹没的概率越高（lost in the middle），且成本随长度线性上升、延迟上升。更关键的是：无关内容会诱导模型答非所问。正确做法是「少而准」，不是「多而全」。

Q5 压缩历史时，什么东西绝对不能丢？

要点：① 用户明确的约束（不做 X、必须用 Y）；② 已经确认的事实/结论（避免重复查）；③ 未完成的待办；④ 出错过的路径（避免重犯）。可以丢：冗长的工具原始输出、已解决的中间推理。

Q6 你的 30 条测试集里，哪一类最差？为什么？

要点：要能具体到类型（通常 multi_hop 最差，因为需要跨段拼接，单块检索天然吃亏）。加分项：说清「多跳问题该怎么改」——查询分解（query decomposition）或先检索再二次检索。

Q7 如果老板要求「回答准确率到 95%」，你怎么回应？

要点：先问「哪一类问题的 95%」——事实型可以做到，多跳和开放问题做不到。再问「错了的代价是什么」——客服场景需要兜底转人工，内部工具可以接受。最后给出方案：分层承诺（可答/需人工/拒答）+ 置信度阈值。不承诺一个笼统的 95%。

阶段通关条件

① 五种指标能同时报数并按类型分组；② 拿一条失败 case 能在 5 分钟内定位到具体层；③ 能解释「为什么混合检索比纯向量好」以及「它为什么不能解决所有问题」；④ Q1–Q7 至少答对 5 题。
