## §1 决策点表

| # | 位置 | 手册做法 | 另一种合理做法 | 什么时候该换 | 怎么核你那份 |
|---|---|---|---|---|---|
| 1 | L8 `MAX_SAME_CALL = 2` | 同工具同参数**最多 2 次** | 3 次（给模型一次自纠机会） | 工具是只读且幂等时，可以放宽到 3 | 数一遍：第 3 次调用是被拦还是放行 |
| 2 | L20 去重 key | `工具名 + md5(json(sort_keys=True))[:8]` | 完整 args 元组当 key | 参数里有巨大字符串（整篇文档）时，哈希省内存 | 换个键顺序，看会不会被当成新调用 |
| 3 | L22 哈希截断 | 8 位十六进制 = 32 bit | 不截断 | 调用次数上百万时有碰撞风险 | 碰撞概率约 `n²/2^33`，一万次调用约 1%——量小可以忽略 |
| 4 | L24 计数语义 | **累计**（`> MAX`） | 连续重复才拦（中间插别的调用就清零） | 模型「查A→查B→查A→查B」这种交替循环，累计式抓得住，连续式抓不住 | 交替两个参数各 3 次，看第 5 次被不被拦 |
| 5 | L31 预算边界 | `>` （恰好等于上限放行） | `>=` | 预算按「预留」算（先扣后调）时该用 `>=` | 恰好传 `MAX_TOTAL_TOKENS`，看返回 None 还是字符串 |
| 6 | L30 预算累加 | 调用方显式传 `add_tokens` | 从 API 响应里自动读 usage | 自动读更省事，但要求每次调用都拿到 usage（流式下要等结尾） | 你那份是「谁算 token」——算的人不同，漏算的位置也不同 |
| 7 | L41 非 JSON | 放行，交给模型读 | 判不合格 | 你的工具全部约定返回 JSON 时，非 JSON 就该拦 | 传一段纯文本，看 ok 是 True 还是 False |
| 8 | L42 非 dict | 放行（数组也是合法 JSON） | 要求必须是 dict | 需要 `{"rows": [...]}` 这种包装时 | 传 `[1,2,3]`，看拦不拦 |
| 9 | L44 校验深度 | 只查**顶层**，`None` 也算缺失 | 递归查嵌套 | 数据结构深（RAG 的 `{"chunks":[{"text":...}]}`）时，只查顶层等于没查 | 传 `{"data":{"rows":null}}`，看能不能发现 |
| 10 | 校验触发点 | 由调用方决定何时调 `check_result_schema` | 在 Registry 层统一拦 | 统一拦不会漏，但纯文本工具要给白名单 | `grep -c check_result_schema`，和「返回 JSON 的工具数」对得上吗 |

第 9 条是最容易高估的一条：**只查顶层意味着深层脏数据完全漏网**。手册的 `{"data": null}` 例子能被抓住，
但真实 RAG 返回是 `{"chunks": [{"text": null}]}`，顶层 `data` 存在且非 null，**照样放行**。

## §2 静默错误清单

| 静默错误 | 现象 | 什么时候暴露 |
|---|---|---|
| key 不含参数 | 每个工具只能调一次，第二次起全被拦 | 正常任务就被误杀，最容易被发现——但也最容易被误判成「模型在偷懒」 |
| key 不含工具名 | 两个工具用同一个参数就互相算重复 | 很少见，但一旦发生极难查 |
| 哈希前不 `sort_keys` | 键顺序变了就当成新调用，检测漏掉一半 | 换一家 provider 后突然「模型开始乱调工具」 |
| 边界写 `>=` | 恰好用满就被拦，报错信息说「已用 60000 超过 60000」 | 自相矛盾的日志 |
| 预算按单次算 | 每轮都「没超」，跑一天烧光 | 月底账单 |
| 非 JSON 判不合格 | 纯文本工具全部报错，模型收到「缺字段」这个错误理由 | 会一直重试同一个调用，看起来像死循环 |
| `MAX_STEPS` 声明了不检查 | L7 有这个常量，但本文件里没有任何地方用它 | 见 §3，这是真事 |

## §3 参考实现里的两处事实

1. **`MAX_STEPS = 8`（L7）在本文件里从未被使用**。它要么是给 loop 用的（那就该在 loop 里判，不该放这里），要么是死常量。判断标准很简单：`grep -rn MAX_STEPS` 除了定义处还有没有第二处。
2. **`check_result_schema` 只查顶层**（L44）。这不是 bug，但要知道它的覆盖边界——见 §1 第 9 条。

## §4 一个容易混的概念

「拦截信息」和「异常」是两种东西，别混：

| | 返回字符串 | 抛异常 |
|---|---|---|
| 谁处理 | 模型（它看得到消息，会换条路） | 你的代码（try/except） |
| 适合 | 重复调用、预算超了、数据不可信 | 内部 bug、配置错误 |
| 用错的表现 | 把「预算超了」抛异常 → 直接失败，而不是让模型用现有信息作答 | 把「代码崩了」返回字符串 → 模型一本正经地当成工具结果读 |

手册这三层全部用**返回字符串**，因为它们的共同目的是「劝模型换条路」，不是「终止」。
