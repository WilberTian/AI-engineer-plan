# P4-2 接口约定：三层兜底

判分器只看这一页。

## §1 落点与公共名

```
agentlab/resilience/guards.py
    MAX_TOTAL_TOKENS                 int，预算上限（判分要用它算边界）
    LoopGuard()
        .check_call(name: str, args: dict) -> str | None      None = 放行
        .check_budget(add_tokens: int) -> str | None         None = 放行
    check_result_schema(text: str, required_keys: list[str]) -> tuple[bool, str]
```

拦截时返回**给模型看的一句话**（不是异常）。这是刻意的：这三层是「劝模型换条路」，
不是「让程序崩」。崩是 P4-1 注入的 exception 那一类。

## §2 判什么（16 条）

### 重复调用检测（6 条）

| # | 断言 | 为什么 |
|---|---|---|
| 1–2 | 同工具同参数：前两次放行，第三次拦 | `MAX_SAME_CALL=2` 是「最多几次」，不是「第几次开始拦」 |
| 3 | 换参数不误杀 | 只按工具名去重会把「查 A」和「查 B」当成重复 |
| 4 | 参数键顺序不同仍算同一调用 | JSON 键顺序不固定，哈希前必须 `sort_keys` |
| 5 | 不同工具不共用一个计数器 | key 里少工具名就串了 |
| 6 | 被拦之后继续拦 | 只拦一次，第 4 次又放行 |

### token 预算（4 条）

| # | 断言 | 为什么 |
|---|---|---|
| 7 | 没用完不拦 | — |
| 8 | **恰好等于**上限不拦 | `>` 还是 `>=`，差一个字差一整轮 |
| 9 | 超一点就拦，且消息含实际用量 | 不写用量的日志没法判断「该加预算还是该收需求」 |
| 10 | 按**累计**算 | 按单次算的「预算」不是预算 |

### 脏数据校验（6 条）

| # | 断言 | 为什么 |
|---|---|---|
| 11 | 缺字段 → 拦，理由含字段名 | `{"data": null}` 被当答案用，就是手册说的那一类事故 |
| 12 | 值为 `null` → 拦 | 缺字段和显式 null 是一回事 |
| 13 | 齐全 → 放行 | — |
| 14 | 纯文本 → 放行 | 不是 JSON 就没法按字段判，交给模型读 |
| 15 | 截断的 JSON → 放行（按非 JSON 处理） | 判成「缺字段」的话，模型收到的是**错误理由** |
| 16 | 嵌套里的 null 不拦 | 记录边界：只查顶层 |

## §3 不判什么

- **「五类故障下不抛未捕获异常」**：要把 guards 接进 loop 再打故障，离线判不了。`run_checks` 只判函数本身。
- **「错误信息能回答下一步该做什么」**：这是判断，不是断言。第 2/9/11 条只判「有没有工具名 / 用量 / 字段名」这些可机械核的要素。
- **429 退避**：本卡代码里没有退避实现（那是 p4-3 的事），不判。

## §4 你的自由

- 三层拆成三个函数、三个类、或者一个类三个方法
- `required_keys` 从工具 spec 里自动推导，而不是手写
- 拦截信息措辞随意（判分只查是否含工具名 / 用量 / 字段名）
- 加第四层（比如按时间预算），只要前三层的语义不变

## §5 怎么跑

```bash
python3 labs/p4-2/harness/run_checks.py --target ~/code/agentlab-project
python3 labs/p4-2/harness/run_checks.py --target . --filter 预算
```

## §6 边界

16 条全绿说明**兜底逻辑本身**对了。它不说明你的 agent 在故障下真的「不崩 + 可读」——
那要把 guards 接进 loop，打五类故障各跑一遍。那一半必须真跑。
