## §1 决策点表

| # | 位置 | 手册做法 | 另一种合理做法 | 什么时候该换 | 怎么核你那份 |
|---|---|---|---|---|---|
| 1 | 聚合维度 | 按 `span.name` 聚合 | 按 `name + kind` 两级 | 同名 span 跨 kind（`retrieve` 既是工具又是检索）时 | 打印 `{kind: {name: cost}}` 看一眼 |
| 2 | 成本口径 | 只算 llm 的 token | 检索/重排按「查询 embedding 成本」估 | 重排用的是 cross-encoder（也要算 GPU/API 钱） | 你的总额和账单对得上吗 |
| 3 | 耗时口径 | 同名累加 | 取 p95 而不是累加 | 想知道「最慢那次」时 | 累加会被调用次数带偏——调 100 次必然大 |
| 4 | 排序键 | 成本降序 | 耗时降序 / 双列 | 要优化延迟时按耗时排 | 你的表第一行是不是真的最大 |
| 5 | 单价来源 | 模块级常量 | 从 `PRICES` 表按模型取 | 一个 run 里混用多个模型时**必须换** | 你的 span 有没有 model 字段 |
| 6 | 分母 | 所有 llm 成本之和 | 整个任务成本（含工具/检索） | 要回答「模型占几成」时必须用后者 | 占比加起来是不是 100%——只算 llm 就必然 100% |
| 7 | 输出 | print + 返回 | 只返回，由调用方打印 | 要进 eval 报告时 | 你的 breakdown 有没有 print 副作用 |

第 5 条是最容易被忽略的：**手册用两个全局常量，意味着整个 run 只能有一个模型的价格**。
一旦你做了 p4-9 的模型路由，同一份 trace 里就有三档模型，这时候常量就不够用了——
你必须从 span 上读 `model` 字段再查表。这是 P4-9 和 P4-13 的接口处，两份代码合起来才会暴露。

## §2 参考实现的问题：检索与重排被丢掉（判分器已抓住）

```python
for s in trace.spans:
    if s.kind != "llm":
        continue          # ← 检索、重排、工具全部跳过
```

卡里正文要求「把成本拆到每一次模型调用、**每一次检索、每一次重排**」。代码只做了第一类。

**为什么这不是小事**：那道面试题里，正确答案的第一步就是分解。如果分解表只覆盖模型调用，
你会看到「100% 的成本在模型上」，于是直接跳到「换小模型」——恰好是题目里说的那个错误答案。
真实的成本结构可能是：模型 45%、重排 40%（cross-encoder 很贵）、检索 15%。

**修法**：`retrieval` / `rerank` 的 span 也要出行，成本按它们自己的计价方式算（embedding 按 token、
cross-encoder 按 GPU 秒或 API 单价）。哪怕先记 0，也别丢——**丢掉的 span 会让占比失真**。

## §3 静默错误清单

| 静默错误 | 现象 | 什么时候暴露 |
|---|---|---|
| 只算 llm | 占比永远 100% 在模型上 | 优化方向选错，改了半天没效果 |
| 同名不合并 | 表有 200 行，看不出重点 | 你会手动 Excel 排序，然后再也不打开这张表 |
| 耗时取累加 | 「重排最慢」（其实调了 50 次） | 你去优化一个本来就不慢的环节 |
| 单价写死一个模型 | 混合模型的 run 成本算错 | 上线路由之后 |
| 分母用 llm 总额 | 占比加起来永远 100% | 没人会怀疑它，因为它「看起来对」 |
| print 在函数里 | 进 eval 报告时刷屏 | 批量跑 200 条时 |

## §4 这道题真正考什么

代码只有 27 行，判分器能判的也就 12 条。但那道题的杀伤力不在这里。

题目给的是：`$0.4 / 9s / 78% → $0.1 / 3s / ≥70%`。

**错误答法的共同点**：一上来就给方案（「换小模型」「加缓存」「上流式」）。
**正确答法的共同点**：先说「我要先跑一次分解」，再说「如果 70% 在某个调用上，那就……」。

所以这段代码的价值不是它能算，而是**它让你在面试里能说出具体数字**：

> 「我跑了一次 breakdown，发现 62% 的成本在三次 self_check 上——因为它在每一轮都被调用一次，
> 而上下文在累积。所以第一步不是换模型，是把它改成只在低置信时跑。」

这句话里每个数都来自这张表。没有表，你只能说「我觉得可能是……」。

顺带一个可核的判据：**如果你的分解表第一行占比 <30%，说明你的成本是分散的**，
这时候任何单点优化都不会有效，正确做法是先削减轮次（成本延迟双杀），而不是调单价。
