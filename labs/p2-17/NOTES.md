## §1 决策点表

| # | 位置 | 手册做法 | 另一种合理做法 | 什么时候该换 | 怎么核你那份 |
|---|---|---|---|---|---|
| 1 | 存储格式 | 单个 JSON 文件，`{key: Memory}` | SQLite / Redis / 一张表 | 记录超过 500 条、或要按用户隔离时 | 你的 `save` 是全量重写还是增量？全量在 1 万条时会是瓶颈 |
| 2 | 键设计 | 稳定语义键 `personal.diet` | 自增 id + 向量 | 要支持「同一件事多个版本」时 | 同义表述（「不吃辣」「忌辣」）会不会写成两条 |
| 3 | 冲突策略 | 后写覆盖（`updated`） | 并存 + 时间戳，注入时取最新 | 要保留历史（审计/回溯）时 | 改主意后注入的是新值还是两条都有 |
| 4 | 去噪 | 同值返回 `noop` | 记 `last_seen` 但不再存一条 | 想知道「这条被确认过几次」时 | 重复说同一件事，store 会不会变长 |
| 5 | 注入时机 | 每轮按 query 召回 | 会话开始时一次性注入 | 记忆多、query 变化大时用前者 | 你的 system 里是全量还是按需 |
| 6 | 注入条数 | `k=5` | 按 token 预算截断 | 单条记忆很长时 | 5 条 × 200 字 = 1000 字，能接受吗 |
| 7 | 排序 | 偏好优先 | 按相关度 + 时间衰减 | 偏好很多时（10 条以上） | 你最想让它记住的那条排在第几 |
| 8 | 召回算法 | 关键词子串 | 分词 / 向量 | **中文必须换**，见 §2 | 用「我吃辣吗」测一次 |
| 9 | 写入门槛 | 无（什么都写） | 只写「长期有效」的事实 | 记忆被噪音污染时（「今天下雨」也记住了） | 一周后 store 里有多少条是废话 |

第 9 条是实际使用中最先暴露的问题。手册这段代码没有门槛——`upsert` 来者不拒。
于是「我今天有点累」也会变成一条 `kind=fact` 的记忆，三天后注入时占掉 k=5 里的一个位置。

判断标准：**这条信息半年后还有效吗**。有效的（不吃辣、父亲是医生、在上海）写；无效的（今天下雨）不写。

## §2 参考实现的问题：中文查询召不回（判分器已抓住）

```python
hits = [m for m in store.values() if any(w in m.value for w in query.split())]
```

| 查询 | `query.split()` | 结果 |
|---|---|---|
| `"我 吃辣 吗"`（带空格） | `["我","吃辣","吗"]` | 命中（`"吃辣" in "不吃辣"` 为 True） |
| `"我吃辣吗"`（正常中文） | `["我吃辣吗"]` | **不命中** |

**为什么危险**：英文语境下这段代码完全正常（英文天然有空格），
你写测试时大概率也用英文或带空格的短语，于是全绿。上线后中文用户 100% 无记忆。

**修法**（按成本排序）：

1. **字符 n-gram 重叠**（最便宜）：把 value 和 query 都切成 2-gram，算重叠比例，超过阈值算命中
2. **双向子串**：`w in v or v in w`，再按长度加权——对「吃辣」vs「不吃辣」这种部分重叠够用
3. **jieba 分词**：`jieba.lcut(query)` 取名词性词，再匹配——最准，多一个依赖
4. **向量**：复用 P2 的 embedder，最贵也最通用

## §3 静默错误清单

| 静默错误 | 现象 | 什么时候暴露 |
|---|---|---|
| `query.split()` 切中文 | 中文永不召回 | 只有中文用户会发现，英文测试全绿 |
| 冲突时并存 | 注入两条矛盾的偏好，模型自己打架 | 用户改主意之后 |
| 同值也存 | store 无限长，注入被噪音占满 | 两周后 k=5 全是重复 |
| `save` 只在退出时调 | 进程被 kill 就丢 | 部署重启之后 |
| 记忆里存了敏感信息 | 明文落在磁盘上 | 合规检查 / 数据泄露 |
| 没有 `source` | 出问题查不到是哪次会话写错的 | 用户说「它记错了」时 |

最后一条很实际：用户说「你怎么记得我不吃辣？」——如果 `source` 在，
你能翻回那次会话看他是不是说了；没有就只能猜。

## §4 三种存储格式的取舍（卡里第 ③ 条要你答的）

| 格式 | 写 | 读 | 跨会话 | 适合 |
|---|---|---|---|---|
| 单 JSON 文件（手册） | 全量重写 | 全量加载 | 是 | <500 条、单用户 |
| SQLite | 增量 insert/update | 按 key 或 FTS 查 | 是 | 上千条、要事务 |
| 向量库 | 需要 embedder | 语义检索 | 是 | 记忆多、查询口语化 |

手册选文件格式的理由是**够用**：一个人的记忆通常几十条，全量读写 <1ms。
换成 SQLite 的代价是多一层依赖和一次 schema 迁移，收益要等条数上来才体现。

**这个理由就是卡里第 ③ 条要的答案**——不是「JSON 更好」，而是「这个量级下 JSON 的成本最低，
上量再换」。答不出这句，说明你只是抄了一个方案，没做取舍。
