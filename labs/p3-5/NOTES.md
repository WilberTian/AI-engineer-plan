## §1 决策点表

| # | 位置 | 手册做法 | 另一种合理做法 | 什么时候该换 | 怎么核你那份 |
|---|---|---|---|---|---|
| 1 | 分段依据 | 按稳定性（5 段） | 按职责分（更多段） | 某段内容变化频率不一致时 | 数一下每段「多久变一次」 |
| 2 | 动态段位置 | 最后 | 塞进 user 消息（和 P3-12 的状态栏合并） | **推荐换**：放进 user 就完全不碰 system 前缀 | 看 system 里还有没有会变的东西 |
| 3 | 文件数 | 每次数目录 | 缓存 5 分钟后重数 | 语料上千个文件时（glob 也不便宜） | 计时一次 `build_system` |
| 4 | `extra` 位置 | 最后 | 并入 user 消息 | 任务级补充说明本来就属于「本轮」 | 看 extra 变了前缀动不动 |
| 5 | 工具 schema | 单独传 | 拼进 system 的固定段 | 拼进去的话它进前缀（好：能缓存；坏：加工具就废缓存） | 加一个工具试试前缀变没变 |
| 6 | few-shot | 无 | 放静态段（能缓存） | 需要稳定输出格式时 | few-shot 放在动态段就是每次清缓存 |

第 2 条是这张卡最实际的改法：**「当前环境」根本不必进 system**。
它放进 user 消息（P3-12 的状态栏就是这个位置），system 就变成真正的常量，
前缀永不变——这比「把动态段排到最后」更彻底。

## §2 为什么「前缀稳定」值得单独判

排错了的代码**看起来完全正常**：五段都在、顺序读着顺、输出通顺。
唯一的症状是缓存命中率 0，于是延迟和成本一起回来。

```
parts = [dynamic, IDENTITY, BOUNDARIES, TOOL_RULES, OUTPUT]   # ← 只挪了一下
```

这一行造成的差别：每轮请求的前缀都不同 → `cached_tokens` 恒为 0 →
「缓存开了但没用」→ 而你去查缓存配置，查半天查不出问题（配置是对的）。

判分器的做法是把模块里的 `datetime` 换成假钟，让两次调用落在不同分钟，
再算公共前缀。**这是唯一能在离线环境里证明「前缀稳定」的办法**——
不然两次调用一字不差，什么实现都能过。

顺带一个方法论：这条判据用「公共前缀长度 ≥ 最后一个静态段结束位置」表达，
而不是「两次输出前 100 字相同」。**阈值要绑在结构上，不要绑在魔数上**——
否则你多写一段就被判红。

## §3 静默错误清单

| 静默错误 | 现象 | 什么时候暴露 |
|---|---|---|
| 动态段排在静态段前 | 缓存命中率恒 0 | 账单和 p95 同时变差，查缓存配置查不出问题 |
| `extra` 插到中间 | 换任务就清一次缓存 | 交互式场景（每轮都带不同 extra）掉得最狠 |
| 文件数写死 | 模型以为语料只有 5 篇 | 语料涨到 500 篇，模型还在说「资料很少」 |
| 段间靠 `\n` 拼接 | 读起来黏在一起，改一段容易串到下一段 | 维护时改错段落，排查半天 |
| 空 extra 留标题 | `本次任务补充说明：` 后面什么都没有 | 模型开始「猜测你要补充什么」 |
| 段内容互相重复 | 同一规则说两遍（一遍在边界、一遍在工具） | 改了一处忘另一处，两句互相矛盾 |

最后一条值得单独说：**「不能修改文件」这条规则，写进「能力边界」就够了**。
如果同时写进「工具使用规则」，某天你放开写权限改了边界，工具规则里那句还在——
模型会收到互相矛盾的指令，而两处都在 system 里，日志里看不出来。

## §4 一个判断：值不值得拆五段

拆段的目的有两个，**只有第一个是稳定的收益**：

1. **改一段不牵动另一段**——这是代码维护性，一定成立
2. **更容易命中前缀缓存**——这个要看你的动态内容有多少

如果所有内容都是静态的（没有时间、没有文件数），那拆不拆段对缓存没有影响，
收益只在维护性上。反过来说：**如果你的 system 里只有一处会变的东西，
先把它挪出去（放进 user），收益比拆八段大得多。**

判断方法：把 `build_system()` 的返回值哈希一下，连着跑 10 轮，
看有几个不同的哈希。**10 轮 1 个哈希 = 缓存能全命中；10 轮 10 个 = 缓存等于没开。**
这只要两分钟，比读文档快。
