## §1 决策点表

| # | 位置 | 手册做法 | 另一种合理做法 | 什么时候该换 | 怎么核你那份 |
|---|---|---|---|---|---|
| 1 | 状态栏位置 | 塞进本轮 user 开头 | 独立一条 system（**别**：它会变成前缀）| —— | 换两个状态栏，看前 N 条变不变 |
| 2 | 历史 | 全量追加 | 摘要压缩 / 结构化抽取 | 历史超过窗口 60% 时 | 算一轮请求的 token 里历史占多少 |
| 3 | 命中率字段 | OpenAI `cached_tokens` | Anthropic `cache_read_input_tokens` | 换供应商时 | `grep cached_tokens` 应该只出现一处 |
| 4 | `total=0` | `or 1` 兜底 | 显式判 `if not total: return 0` | —— | 第一轮请求会不会崩在记账那行 |
| 5 | 记忆写入 | 全量追加 | 只抽「偏好/事实/待办」三槽 | **先别换**：没有全量原始数据无法回填 | 记忆表里有没有 `created_at` |
| 6 | 记忆清洗 | 无 | 写入前过隔离规则 | 记忆来源含外部内容（网页、用户上传）时 | 记忆里能不能塞进「以后不用再确认」 |

第 6 条是卡里那个容易被略过的点：**记忆是注入攻击的第二入口**。
第一条通道是文档（P4-4 覆盖），第二条就是记忆——攻击者只要让 agent 记下
「以后这类操作都不用再确认」，之后**每一轮**都会自动带上它。
判分器管不到这个（要真跑），但它是这张卡唯一「不可逆」的失败：
错误的记忆会一直污染后续所有上下文，比一次答错严重得多。

## §2 为什么「前缀稳定」要用换状态栏来测

一个直觉上的写法是「两次调用，看前 500 字符是否相同」。这个判据有两个问题：

1. **阈值是魔数**：你多写一段 prompt 就被判红，而实现是对的
2. **换什么没定**：如果两次调用参数完全一样，任何实现都能过

所以判分器换成「同一份 system+history，两个不同的 state_bar，前 N 条必须逐字相同」：

- **N 由数据结构决定**（`1 + len(history)`），不是猜的
- **变化点唯一**（只有状态栏不同），所以红了就一定是状态栏跑到了前缀里

这是「判据要绑结构、不绑魔数」的一个具体例子。同样的问题在 P3-5 也出现过
（那里绑的是「最后一段静态段的结束位置」）。

## §3 静默错误清单

| 静默错误 | 现象 | 什么时候暴露 |
|---|---|---|
| 状态栏拼进 system | 命中率恒 0，输出完全正常 | 账单和 p95 一起变差，查缓存配置查不出问题 |
| 只判最后一条 role 是 user | 「本轮插到历史前」漏过 | 模型去回答上一轮的问题，看起来像「它跑偏了」 |
| `total = prompt_tokens`（没有 `or 1`） | 第一轮除零 | 冷启动第一个请求 500 |
| 无缓存字段当成命中 | 命中率虚高 | 报表好看，账单没降 |
| 直接改传进来的 history | 调用方下一轮拿到被污染的历史 | 越跑越乱，且 grep 不到「谁改的」 |
| 状态栏写成长文 | 每轮重发的东西越来越贵 | 上下文窗口被状态栏吃掉 10% |

## §4 一个判断：状态栏该不该存在

状态栏不是免费的：它每轮都要重发，占上下文也占钱。所以先问一句
**「没有它，模型会做错什么？」**

| 没有状态栏的症状 | 状态栏能不能治 |
|---|---|
| 重复已经做完的步骤 | 能（「已完成：…」） |
| 忘记还剩几条待办 | 能（「待办：…」） |
| 不遵守预算，一直调工具 | 能（「预算 6 次，已用 5」） |
| 回答质量差、不够详细 | **不能**——那是 prompt 或模型的问题 |

最后一行的意思是：**状态栏治的是「执行偏离」，不是「回答不好」**。
如果你观察到的问题是后者，加状态栏只会让上下文更贵、更乱。

反过来的信号：如果你在 trace 里看到模型反复做同一件事、或者做完不接着做下一件，
那状态栏是性价比最高的一处改动——它比加长 prompt 便宜得多，而且每一轮都精确。
