## 4（重点）：卡正文与参考实现对不上的两处

卡正文 p1-13 有两段「硬要求」，但 122 行的参考实现**两样都没有**：

| 卡正文说 | 参考实现 |
|---|---|
| 「**为什么一定要并发**：10 条串行 × 20 秒 = 3 分钟…并发到 5 路是 40 秒，这才是能坚持每天跑的量级」 | L71-88 是**纯串行** `for c in cases:`，没有 asyncio / ThreadPool |
| 「**为什么值得做缓存**：按 case 内容哈希缓存响应，只在改了 prompt 或换了模型时失效」 | 完全没有缓存逻辑 |

这不是笔误，是两种未完成：

- **照抄代码**的人会得到一个每天要等 3 分钟的 runner，第二周就不跑了
- **照抄正文**的人会以为代码里有并发，去读却找不到

我建议的补法是**先不做并发，先做缓存**。理由：并发会破坏 `avg_latency_ms` 的可比性（5 路并发下单条延迟被排队影响），而缓存只影响耗时不影响判据。顺序反了会得到「很快但数字不可信」的 runner，那比慢更糟。

缓存的最小形态（不改任何判据）：

```
evals/.cache/<sha1(case内容 + prompt版本 + 模型名)>.json   ← 存 answer
命中就用缓存的 answer 走同一条 judge
```

`prompt 版本`必须是显式常量（如 `PROMPT_V = 3`），不能用 system 内容的哈希——否则改一个错别字就把缓存全废了。

判分器不验这两项：验了就等于强加实现方式。
