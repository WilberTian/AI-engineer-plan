# P1-10 要点核对表

写完 `loop.py` 之后用它逐项打勾，看自己哪几处和参考实现不一样、那些不一样是不是错。

行号基于这一版代码块：sha256 前 16 位 `0c68f368ceb9c8a1`（2026-10-31 从 `stage-p1.html#p1-10` 抽出）。
手册改过之后行号会漂，所以每行都附了代码片段当锚点——**行号对不上就看片段**。
跑一次 `tools/verify_reference.py` 会打印当前代码块的 sha256，和上面这个比一下就知道对不对版。

## 1. 怎么用

```bash
python3 labs/p1-10/tools/verify_reference.py   # 先确认参考实现能过判分（改过手册后跑这个）
python3 labs/p1-10/harness/run_checks.py       # 再判你自己的（默认在 ./src 找 agentlab/）
```

然后是三件事，顺序别反：

1. **先跑判分**——协议层不对的话，后两步都没有意义
2. **再核下面 13 条决策点**——差异在这一步才能区分「偏好」还是「错误」
3. **最后才 diff 代码**——写法差异信息量最低，先看会淹没重点

判分全绿只说明协议对了，不代表任务做对了，原因见 §6。

## 3. 决策点（13 条）

「另一种合理选择」不是错，是同一个问题在不同前提下的解。判断标准在倒数第二列。

| # | 定位 | 参考实现 | 另一种合理选择 | 什么时候该换 | 判分管不管 |
|---|---|---|---|---|---|
| 1 | `run()` 签名 | 三个上限入参：`max_steps=8` / `timeout_s=60` / `max_result_chars=2000` | 只留 `max_steps` | 工具很贵（搜索 API、付费模型）时改成金额预算 | 管（第 1 条） |
| 2 | `tool_budget = 6`（在函数体内） | 硬编码，不是入参 | 提成第 4 个入参 | 不同任务要不同预算时 | 不管（自由） |
| 3 | `tool_budget` 与 `max_steps` | **分开计数** | 共用一个计数器 | 一轮只调一个工具可合并；一轮能并调多个**必须分开** | 间接（第 7 条） |
| 4 | `for i in range(max_steps)` | 用 for 当步数预算 | `while True` + 显式计数 + `break reason` | 要在中途区分多种退出原因时 | 不管 |
| 5 | `for tc in msg.tool_calls` | 一轮多个工具**串行** | `asyncio.gather` / 线程池 | 工具是网络 IO 且互不依赖 | 只判「两个都执行」，不判快慢 |
| 6 | 预算耗尽分支 | 仍回一条 `role=tool`（内容「次数已用完」）再 `continue` | 直接 `return` 部分结果 | 没法换：少一条 tool 消息就 400 | 管（第 7 条） |
| 7 | 参数解析的四类错误 | `JSONDecodeError` / 工具不存在 / `TypeError` / `Exception` 分开 | 统一 `except Exception` | 有结构化日志可按 message 聚合时 | 管「不抛」，不管分几类 |
| 8 | `args = {}` 兜底 | 解析失败时给空 dict | 保留原始串 `args={"raw": raw_args}` | 要复盘「模型到底发了什么」时必须改 | 不管 |
| 9 | 未知工具的错误文案 | 「没有名为 X 的工具。**可用：[…]**」 | 只说「工具不存在」 | 不建议换：列候选是让模型自我修正的最低成本手段 | 不管措辞 |
| 10 | 长结果截断 | 截断并回报原长（`...[已截断，原长 N 字符]`） | 静默截断 | 从不 | 管（第 13 条） |
| 11 | `status` 四态 | `done / max_steps / timeout / error` | `ok: bool` | 不做看板、不埋点时可退化 | 间接（第 2、6、12 条各查一个取值） |
| 12 | `messages.append(msg.model_dump(exclude_none=True))` | 原样回填带 `tool_calls` 的 assistant 消息 | 只回填 `content` | 没有「另一种」：漏了下一轮必 400 | 管（第 5 条） |
| 13 | `steps` 与 `messages` 的存法 | `steps` 存未截断原文，`messages` 放截断版 | 两处都截断 | 要做原文回溯时保持现状，要省内存则都截 | 不管 |

## 4. 静默错误（不报错，但结果不对）

这一类比 panic 值钱：崩溃你自己会发现，下面这些只在某天数字对不上时冒出来。

| # | 现象 | 根因 | 怎么自查 |
|---|---|---|---|
| S1 | 模型被告知「最多 6 次」，代码允许的不一定是 6 | 数字 6 出现在两处：SYSTEM 第 4 条、`tool_budget = 6` | 只改一处，看行为变不变 |
| S2 | 埋点里的工具调用次数偏低 | 预算耗尽那次**不产生 `Step`**，但消息发了 | 比 `res.tool_calls` 和 `messages` 里 tool 条数（实测 6 vs 8） |
| S3 | 复盘时查不到模型发的原始参数 | 坏 JSON 时 `args={}`，原文只在 `messages` 里 | 从 `steps` 出发能不能还原第一次调用 |
| S4 | 实际耗时远超 `timeout_s` | 超时只在**每轮开头**检查，单个慢工具跑完才被拦 | 让工具 sleep，看 status 何时变 timeout（实测预算 100ms、实跑 302ms） |
| S5 | 截断后实际长度超预算 | 后缀没算进 `max_result_chars` | 量 `messages` 里那条 content（实测 120 > 100） |
| S6 | 换供应商才 400，本地一直好 | `exclude_none` 漏了，`content: null` 混进请求体 | 打印一次请求体搜 `null` |

S1 是最典型的一类：同一个事实写在两个地方，改一处忘一处，编译过、测试过、行为悄悄变。

## 5. 参考实现的边界

不是 bug，是这份代码**没做到**的地方。写自己的版本时值得知道：

| # | 事实 | 说明 |
|---|---|---|
| G1 | `status` 声明了 `error`，但从未返回它 | 模型调用抛异常时异常直接逸出 `run()`，下游 `if status=="error"` 是死代码 |
| G2 | `Step.kind` 声明了 `stop`，从未使用 | 同一类问题：声明了枚举，没接上实现 |
| G3 | 没有重试 / 退避 / 熔断 | 属 P4（`p4-1` 故障注入），这里故意不做 |
| G4 | `registry._tools.get(name)` 直接摸私有属性（`# noqa: SLF001`） | 因为 P1-9 的 `Registry` 只有 `register/specs/names`，没有公共 `get()`。加一个 `get()` 是合理的改进 |

G1 和 G2 的教训：**声明的枚举要接上实现，否则它只是在文档里好看**。
如果你的版本用 `ok: bool`，反而不会有这个坑——用 bool 不会撒谎。

## 6. 判分覆盖了什么

卡 `#p1-10` 的验收有三条，说清楚哪条能离线判，别以为全绿就万事大吉：

| 卡里的验收 | 判分 |
|---|---|
| ① 三个不同任务能选对工具 | **判不了**。要真模型。判分注入的是脚本化 provider，它「选对」是因为脚本写死了 |
| ② `res.messages` 里能看到完整序列 | **判得最细**（第 3、4、5、7 条） |
| ③ 不存在路径 → 靠同目录候选自我修正 | **一半**。工具层由 P1-9 保证（`read_file` 报错带候选），「模型因此改对」要真模型 |

所以：判分通过 = 协议层对了。它不能替你证明模型用得对——那部分只能真跑，
而真跑的每次结果都不同，**只能当观察，不能当判据**（这也是判分不调真 API 的原因）。

## 7. 扩展到别的卡

这个形态要成立，需要两样东西：

1. **有逐字可指的参考实现**——P1、P3 大致都有（手册里 53 个文件级完整代码块 / 2532 行）
2. **有能离线跑起来的判据**——需要一个假 provider 层。P2 的 eval、P4 的故障注入都能做；
   P5 的真实流量不行，只能写「怎么量」而不是「量出来是多少」

如果某张卡给不出「有两份真实实现」或「能离线判」中的任何一个，就别硬写——
用形容词充数的核对表，比没有更糟。
