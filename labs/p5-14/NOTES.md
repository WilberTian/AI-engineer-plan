## §1 决策点表

| # | 位置 | 手册做法 | 另一种合理做法 | 什么时候该换 | 怎么核你那份 |
|---|---|---|---|---|---|
| 1 | 开关层级 | 远程 > 环境变量 > 默认 | 加文件层 / 加灰度分流 | 要按用户分组开关时 | 三层各设一个值，看谁生效 |
| 2 | 环境变量取值 | 只认 `"1"` | 认 `"1"/"0"/"true"/"false"` | 运维脚本习惯用 `true` 时 | 设 `_FLAG=0`，看它关没关 |
| 3 | 默认关的特性怎么测 | 「关掉它」（**错**，见 §2） | 基线改成「关」，测「开」 | 特性默认是关的时候**必须换** | `replace(BASE, x=False) == BASE` 吗 |
| 4 | 基线 | 每次循环重算（**错**） | 循环外算一次 | —— | 数 `run_eval` 里全开那组跑了几次 |
| 5 | 指标 | Pass@5 + 成本 + p95 | 加护栏：拒答率、错误率 | 卡里那句「护栏击穿就停」 | 报告里有没有护栏那一列 |
| 6 | AB 分流 | 真实用户 | 影子流量 | 小流量下显著性问题 | 算一下最小可检测效应 |

## §2 参考实现的两个问题

这两个都是「跑得通、数字也出来了，但结论不可信」的类型——比崩溃难发现得多。

### 问题 1：基线在循环里重算（判分器第 13 条）

```python
for f in ("query_rewrite", "rerank", "self_check", "cache_prefix"):
    on = run_eval(flags=BASE)                       # ← 每轮都算一次
    off = run_eval(flags=replace(BASE, **{f: False}))
    d_pass5 = on.pass5 - off.pass5
```

实测：全开的基线跑了 **5 次**（4 轮各一次 + `self_check` 那轮 off 恰好也等于全开）。

**为什么这是错的**：`d_pass5 = on - off`，而 `on` 每次都是不同的采样。
于是四个 `d_pass5` 之间的差异里，混进了基线的采样噪声——**你没法比较
「哪个特性更重要」**，而这是消融唯一要回答的问题。

修法一行：

```python
on = run_eval(flags=BASE)                            # 循环外算一次
for f in (...):
    off = run_eval(flags=replace(BASE, **{f: False}))
```

### 问题 2：`self_check` 的消融是空转（判分器第 12 条）

`Flags.self_check` 默认就是 `False`。所以：

```python
replace(BASE, self_check=False) == BASE      # ← 什么都没改
```

这次「对比」两边完全一样，`d_pass5` 恒为 0。**而你会把它读成「自检没有效果，
所以可以砍掉」**——恰恰相反，你从来没测过它。

修法：默认关的特性，基线要改成「关」，测「开」：

```python
BASE_OFF = replace(Flags(), self_check=False)        # 显式声明基线
for f, base in (("self_check", replace(BASE_OFF, self_check=True)), ...):
    ...
```

更一般的做法：**消融测的是「打开这个特性的边际贡献」，所以对比的另一侧应该是
「默认值取反」，不是「一律设 False」**。这一条对任何 `default=False` 的开关都成立。

## §3 静默错误清单

| 静默错误 | 现象 | 什么时候暴露 |
|---|---|---|
| 基线每轮重算 | 四个 delta 不可比 | 想排优先级时排不出来，只能凭感觉 |
| 默认关的特性「关掉它」 | delta 恒为 0，读成「没用」 | 砍掉一个其实有用的特性 |
| 只报通过率不报成本 | 「更准了但贵一倍」看不出来 | 月底看账单 |
| 只报中间量（MRR、命中率） | 机制动了、目标没动也说好 | 评审被问「用户感受到什么变化」 |
| 环境变量 `"0"` 被当成开 | 紧急关不掉 | 出事时手忙脚乱 |
| 没有护栏 | 拒答率翻倍换来 +1 点通过率 | 用户投诉「它什么都不知道了」 |
| 没打 flag tag | 无法按开关分组看指标 | 消融做完了，数据分不开组 |

## §4 一个判断：先消融还是先 AB

手册给了明确顺序：**先消融定位，再 AB 验证**。理由是成本：

| 做法 | 能回答 | 代价 |
|---|---|---|
| 全开 vs 全关 | 这套东西整体有没有用 | 2 次 eval |
| 单特性消融 | 每个特性的边际贡献（**不可加**，因为特性之间有耦合） | 2×N 次 eval |
| AB 测试 | 业务指标有没有变好 | 真实流量 + 显著性所需的样本量 |

跳过消融直接 AB 的典型症状：结论是「整体变好了 2%」，然后**不知道该保留哪个**。
2% 可能是某一个特性带来的 6% 被另一个特性的 -4% 抵掉了——而 AB 只告诉你总数。

另一个更常被违反的前提（手册里那句「我改变的东西，和我真正关心的东西，是同一个吗」）：
你关掉的是「重排」这个**机制**，要证明的是「答案更准」这个**目标**，
中间还隔着 MRR、命中率这些中间量。**只报中间量变好，等于没证明。**

判断你该做到哪一步：
- 只有 1 个特性 → 别做消融，做 AB
- 有 3–6 个特性且互相独立 → 单特性消融值得做（N×2 次 eval）
- 特性之间有强耦合（缓存影响延迟、重排影响成本） → 消融只能给「大概」，最终要 AB
