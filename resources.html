5Harness 与框架：2026 年该看哪几个

这是全站唯一一份项目地图。先看不会害你，先装会害你——P1–P3 一个框架都不要装，但你必须知道地上有哪些东西、各自把控制权放在哪一层。

先给三条能立刻用的结论

① P1–P3 一个都不要装。先手写 loop，再读懂 harness 为什么这么设计。顺序反了，你会把「我不懂」误当成「框架很复杂」。

② 先分清你要的是「循环」还是「一台电脑」。要循环 → 薄 SDK（OpenAI Agents SDK / Pydantic AI / AI SDK 的 ToolLoopAgent）；要电脑（读文件、跑命令）→ harness（Claude Agent SDK / Deep Agents）。这个判断错了，后面所有比较都是白做。

③ 一次 run 活多久，是唯一硬指标。秒级 → 别上框架，这是最常见的过度设计；分钟到天 → 持久化能力决定一切（LangGraph checkpointer / Pydantic AI 接 Temporal / AI SDK 的 WorkflowAgent），其他都能将就。

先说时效

本节的事实核对到 2026 年 10 月。这个领域三个月就会有项目改名、换 license、推翻 API——MCP 在 7 月刚做了历史上最大的一次改动，Vercel AI SDK 在 7 月发了第 7 版并把 P5 里写的几个 API 弃用了。所以：趋势和判断可以信，具体函数名请按官方文档对一遍。

5.1 四个词先分清

新手 80% 的困惑来自这里：把「我手写的那个 while 循环」「LangGraph」「Claude Code」放在同一个抽屉里比较。它们不在一个抽屉。

层它替你做的主它不管什么代表
① 模型 API
最底层		 把 messages 变成回复或 tool_calls 循环、执行工具、重试、上下文压缩——全是你的事 Anthropic Messages API、OpenAI Chat Completions
② 薄 loop SDK 那个 while 循环：收 tool_calls → 调函数 → 回灌 → 再问 不给你沙箱、不给权限系统、不替你想压缩 OpenAI Agents SDK、Pydantic AI、smolagents、AI SDK 的 ToolLoopAgent
③ harness
本页主角		 loop + 内置工具 + 沙箱 + 权限审批 + 上下文压缩 + 会话持久化 + 子 agent 不替你决定产品形态、计费、多人协作 Claude Agent SDK、Deep Agents、Codex CLI、OpenCode、OpenHands、OpenClaw
④ 产品 在 harness 上包 UI、账号、计费、团队权限 它的 loop 你多半看不到也改不了 Claude Code、Cursor、Trae、CodeBuddy
一句话记住

框架给你一个循环，harness 给你一台电脑。「给 agent 一台电脑」意味着它要能读文件、能跑命令、会搞坏东西——所以 harness 的核心难点从来不是 loop，是怎么让它搞坏的范围可控。这也是为什么 Claude Code 的权限系统和 Codex 的沙箱比它们的 loop 更值得读。

你在 P1 手写的那 130 行，在第几层

在 ① 和 ② 之间。你亲手管了 messages 数组、tool_call_id 关联、三种停止条件——这些正是 ② 层替你做的事。写它的价值不是「以后不用框架」，是当 harness 出怪问题时，你知道该往哪一层看。没有这层经验的人，遇到「agent 无限调同一个工具」只能改 prompt；你会先去看 loop 的幂等检查和 budget。

2026 年才稳定下来的三分法

行业里现在把过去统称「agent 框架」的东西拆成三类，这个拆分很有用，因为它直接对应「你该不该用」：

低层编排运行时（LangGraph、LlamaIndex Workflows、Microsoft Agent Framework workflows）——你自己画流程图，它负责跑和存。
batteries-included harness（Claude Agent SDK、Deep Agents、Strands、AI SDK 的 HarnessAgent）——一整台配好的机器，带计划、文件系统、压缩。
薄类型化 loop（Pydantic AI、OpenAI Agents SDK、smolagents）——贴着原生 API，只帮你写循环。

这三类不能互相替代，所以「LangGraph 和 Claude Agent SDK 哪个好」这个问题本身没有答案——它们解决的不是同一个问题。

5.3 五个协议与约定（2026 年已经定型）

2026 年这一层最大的变化不是出了新协议，是协议收敛了：五家互相竞争的公司把各自的规范捐给了同一个中立基金会。这件事对你筛选信息很重要——两年前那种「三种 MCP 竞品、四个 agent 协议」的混乱已经结束，不用再追。

一个日期记住整件事

2025 年 12 月 9 日，Linux 基金会宣布成立 Agentic AI Foundation（AAIF），创始项目三个：Anthropic 的 MCP、Block 的 goose、OpenAI 的 AGENTS.md。到 2026 年 8 月 17 日，Google 的 A2A 也迁了进来；Cisco 的 AGNTCY 同在。会员从不到 40 家涨到 250 家以上，platinum 名单里同时坐着 AWS、Anthropic、Block、Bloomberg、Cloudflare、Google、Microsoft、OpenAI——三家直接竞争的前沿模型公司，在一起共管它们 agent 跑的管道。

对你的实际意义：这些规范的 URL 和组织名会稳定下来，可以放心投入学习；同时也意味着「押注某家私有格式」这件事的风险被官方承认了。

5.4 MCP 2026 大改：从有状态变无状态

如果你的 MCP 知识来自 2025 年的文章，你会写出一套跑在负载均衡后面就挂的实现。这一节是 P3-9 的前置知识。

改了什么之前（2025-11-25）现在（2026-07-28）
握手必须先 initialize / initialized握手取消。版本、客户端信息、能力塞进每个请求的 _meta
会话服务端发 Mcp-Session-Id，后续每个请求都得带，把客户端钉在某个实例上会话头移除。任何请求可落到任何实例，普通轮询负载均衡就行
发现能力握手时交换新增 server/discover（服务端必须实现），客户端想提前知道才调
路由网关要解包 JSON 才知道调用什么Mcp-Method / Mcp-Name 走 HTTP 头，网关和限流器不用拆包就能路由
缓存每次都要重新拉工具列表列表结果带 ttlMs 和 cacheScope，客户端可缓存——顺带让上游 prompt cache 更稳
服务端反向请求常开双向流做 sampling / elicitation改成 MRTR（多轮往返）：工具返回 input_required，客户端带上答案重发原请求
长任务tasks/result 阻塞等Tasks 变成正式扩展：tasks/get 轮询 + tasks/update

「无状态协议，有状态应用」——这句话值得背下来

协议层去掉 session，不等于你的应用不能有状态。官方推荐的做法是：需要跨调用带状态的 server，自己生成一个显式句柄（basket_id、browser_id），让模型把它当普通参数传回来。他们说这比藏在传输层的 session 更好用——因为模型看得见这个句柄，可以自己接。

这背后是一条通用的架构直觉：把隐式状态变成显式参数，系统就更容易水平扩展，也更容易调试。面试里能说出这句，比背规范条文有用。

对你 P3-9 的具体影响

你按计划写的是 stdio 传输的本地 server ——这块不受影响，照写。
但只要你想改成 HTTP 给远程客户端用，就别照任何 2025 年的博客：不要写 initialize 处理、不要维护 session 字典、记得返回 ttlMs。另外 Tier 1 SDK（TypeScript / Python / Go / C#）在发布当天就跟上了，先升级 SDK 再看文档，别拿旧版 SDK 去实现新规范。

Build vs Buy：OpenHands 自己给的建议反而最值得听

一家卖 harness 的公司，官方论点是：租运行时，别 fork。定制的顺序是 prompt → MCP server → skills/插件 → SDK，从最轻的往上走，走到 SDK 还不够才考虑 fork。

5.11 这一节也会让你踩的坑

坑为什么它会害你怎么改
同时读三个 harness 每个都有自己的一套术语（session / thread / run / task），三套混在一起会让你连「我在读哪个概念」都分不清 一次只读一个到能改，读完再换。W10–W13 只碰两个仓库（learn-claude-code + claw0）
上手就用 Claude Agent SDK 它替你做完了所有决定，你跑通了也不知道为什么能跑通。出了问题只能改 prompt P1 手写 loop 是前提，不是可选。先有「我知道它在替我做什么」，再用它
把某个 harness 的系统提示当最佳实践抄 那些 prompt 是针对特定模型、特定工具集调出来的，模型一换就失效；而且很多是对着评测集过拟合的 抄结构（身份 / 边界 / 工具规则 / 输出格式 / 动态段），不抄句子。P3-5 就是干这个的
追周更框架的版本 LangChain、Mastra、Pydantic AI 是周更级别。你追版本的时间足够把 loop 重写两遍 锁定一个版本，季度看一次 changelog。只有碰了才知道疼的地方才升级
把「我装过 X」写进简历 装过等于没学过。面试官一句「它内部怎么做的」就露底了 写「我读了 X 的 Y 模块，因为我遇到了 Z 问题」。问题比工具值钱
以为框架选型是一次性决定 这个品类十八个月里 LangChain、CrewAI、Pydantic AI、Agno、Haystack、ADK 全做过大版本重写，微软把两个框架合并进第三个 假设你会在一年内换一次。把业务逻辑和框架的接触面压到最小，就是为换做准备
最后一句

这一节列了二十多个项目，但你真正会用到的可能是三个：一个读（claw0 / learn-claude-code）、一个对照（OpenHands 或 OpenCode）、一个做产品（AI SDK 的 ToolLoopAgent）。其余的价值是让你在面试里听到任何名词都不慌，以及在别人说「用 X 就行了」时，你知道该问哪四个问题。

11怎么读 benchmark 分数（面试加分项）

三个必须知道的陷阱

① 分数属于「模型 + harness」的组合，不属于模型。同一个模型换一套工具和轮数预算，分数会差很多。所以「某模型 SWE-bench 80%」不等于「你用它能到 80%」。
② 公开 benchmark 会泄漏进训练数据。越老越有名的越不可信（GAIA 已公开多年），看分数先看它「还有没有区分度」。
③ 饱和就失去意义。SWE-bench Verified 顶部已接近饱和，且 OpenAI 在 2026 年初因测试缺陷与污染停止报告它。你要做的是用 30 条自己的 case，而不是追排行榜。

面试话术：「排行榜我只看趋势，选模型还是用自己的 30 条集跑一遍——因为公开 benchmark 已经泄漏，且分数是模型加 harness 的组合，在我的工具集上不成立。」

14《深入理解 AI Agent》按周读法

李博杰《深入理解 AI Agent：设计原理与工程实践》（2.0 版，10 章 + 109 个配套实验）。它不替代这份计划——计划管「这周敲什么命令」，它管「为什么这条命令要这么设计」。两边对不上时以动手为准：书上写了但你没跑过的，面试里说不出口。

全书只有一个公式

Agent = LLM + 上下文 + 工具。三者分别对应强化学习的策略、观察空间、动作空间。所有章节都在这三项上做工程：LLM 怎么调（第 2 章 §API 的上下文结构）、上下文装什么（第 2、3 章）、工具怎么设计（第 4 章）、怎么度量（第 7 章）、怎么变好（第 9 章）。

读完的判据只有一条：能不能回答「这个设计换掉会怎样」。答不出来，说明只读到了概念层，没读到工程层。

14.4 四条阅读纪律

纪律一

先读结论，再读推导

每节开头先看小结段，能自己讲明白就跳过推导，讲不明白再往回读。这本书的推导密度高，逐字读会卡死进度。

纪律二

只做服务当前作品的实验

W09 做 7-3（Rubric 评估）是因为 P2 正好要写 eval；W04 做 2-3（错误上下文模式）是因为你正在手写 loop。跟当前作品无关的 ★★ 实验一律跳过。

纪律三

每章写三条「换掉会怎样」

读完一章，在页面笔记里写三条：这个设计如果换成另一种会怎样。写不出来就是没读懂。W23 的表达训练直接用这些笔记。

纪律四

它占预算的 15%，不能更多

250–290 小时里给读书留 40 小时左右，也就是每周 1.5–2 小时。读书时间超过动手时间，这个计划就失效了。

15术语表（面试前扫一遍）

这些词你后面每天都会用。面试里说错一个定义，比不知道更伤——因为它说明你只是背过。下面每个都是「一句话准确定义」，不是科普。

术语一句话解释
Agent由模型自己决定下一步做什么、调用什么工具的系统（区别于由代码写死流程的 workflow）
Harness模型外面的那套「车架」：循环、工具、权限、上下文管理、错误恢复。模型是司机，harness 是车
ReAct推理 → 行动 → 观察 的循环范式，绝大多数 agent 的骨架
Tool / Function calling让模型输出结构化参数来调用你的函数；可靠性取决于 schema 与描述质量
MCP模型上下文协议，把「工具与数据源」标准化成可复用 server 的开放协议。2026-07 起协议核心为无状态（无握手、无会话 ID），见 本节 5.4
A2AAgent2Agent，让不同厂商的 agent 互相发现与委派任务的协议（横向）；MCP 是纵向。2026-08 并入 AAIF
Agent SkillsSKILL.md 开放格式：可移植的「怎么做某件事」知识包，靠 description 触发、按需加载正文
RAG检索增强生成：先从你的数据里找依据，再让模型基于依据回答
Embedding把文本压成向量，用距离表示语义相似
Rerank对初筛出的候选做二次精排，通常能明显提升前几名质量，代价是延迟
RRF倒数排名融合（Reciprocal Rank Fusion），把多路检索结果合并的常用方法，只看排名不看分数
Context engineering管理模型每次看到的所有 token（提示、检索、历史、工具结果），目标是「最少的高信号 token」
Context rot上下文填得越满、模型越不准的现象（不只是「装不下」）
Compaction把历史压缩成高保真摘要，腾出窗口继续干活
Eval评测：用固定测试集 + 评分器衡量系统质量，并做回归
LLM-as-judge用模型当评分员；要防位置偏好、长度偏好、自我偏好三种偏差
Trace一次任务全链路的分步记录：每步输入输出、耗时、token
HITLHuman in the loop，人在环上：关键动作前需要人确认
Prompt injection不可信内容（网页 / 文档 / 工具返回）试图改变系统行为的攻击
Idempotency同一个操作重复执行不会产生额外副作用——重试的前提
Blast radius一次错误操作的影响范围；越小越安全
Checkpoint把执行状态存下来，可以中断、恢复、回放
Durable execution持久执行：进程挂了、部署重启了，任务从上次的步继续，而不是从头再来。长任务选框架时这是唯一硬指标
Sandbox限制 agent 能碰到什么的执行边界。注意粒度：Claude Code 的 Bash 沙箱只管 shell 命令，文件工具和 MCP 在沙箱外；Codex 默认网络关闭
最后一条建议

这份清单里 80% 的价值在前 8 项「官方必读」和 11 个「读源码」仓库。工具类的东西等你撞到问题再查——没有问题的学习，留不下东西。
